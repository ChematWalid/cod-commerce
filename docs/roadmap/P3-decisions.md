Decisions taken while building phase P3. Each row gives the decision, why, and the cost if it proves wrong. Blocks: coordinator D3000–D3099, P3.S1 D3100–D3199, P3.S2 D3200–D3299, P3.S3 D3300–D3399, P3.S4 D3400–D3499, P3.S5 D3500–D3599.

| D3214 | Storefront in-process host LRU: 10 000 entries, 60 s positive, 15 s negative (#180); hosts outside `<label>.<PLATFORM_DOMAIN>` get 404 with no api call while custom domains are stubbed (P8.S9). Search results are not stored in the shared cache. Cache safeguards (#120): 512 KB entry cap, `{APP_ENV}:cache:writes-off` switch set by a 30 s memory guard at 60 % of `maxmemory`, 250 ms command timeout treated as a miss (#121), tag index as a sorted set scored by expiry and pruned on write and revalidate (#183). | ADR 0006 §4 values; noeviction Valkey shared with BullMQ. | Tuning constants. |
| D3215 | The storefront stays on port 3001 (`demo.localhost:3001`); the brief's `:3000` is the api port. | `.env.example` and scripts already use 3001. | — |
| D3216 | Task 7 details of D3214: (a) a tag revalidation reads the index (`ZRANGE`) and then, in one `MULTI`, deletes those entries and `ZREM`s only those members (plus the expired-score prune), rather than deleting the whole index: an entry indexed between the read and the `MULTI` keeps its member, so the next revalidation still reaches it. (b) The 250 ms timeout wraps every handler command (`cache/command-timeout.ts`, a race; the command itself still completes) and the client also gets `socket.connectTimeout` 1 s and `commandsQueueMaxLength` 1000. (c) The memory guard polls lazily, at most every 30 s on the next entry write, instead of a background timer; reads and revalidations are never gated. (d) The storefront validates its own `PLATFORM_DOMAIN` like the api: required in staging and production, `localhost` elsewhere; compose passes the api's value. | Deleting the whole index could leave a concurrently written entry unindexed for up to 6 h; a timer would run during `next build` and in tests. | A plain `DEL` of the index if the race is judged harmless; a timer if writes are too rare to poll. |

(b) `VisibleCollection.featuredAsset.preview` (P2.S3) still answers the absolute URL of `toAbsoluteUrl`; the storefront-api maps the two to one shape (Task 6b). (c) `visibleMemberIds` names every member, hidden, draft and sold-out products included, with no cap: visibility comes from the projection join (D3206). (d) `findVisibleBySlug` reads the slug in the store channel (`CollectionService.findOneBySlug`) and then the store's definition, so another store's collection with the same slug never answers. (e) The #246 and preview unit cases live in `catalog-read-public-shape.test.ts` and the collections cases in `collections-read-lookups.test.ts` / `collections-public-lookups.int.test.ts`, since the existing files are near the 300-line cap. | One read per page (no N+1); paths keep the storefront's image loader the only place that builds URLs (D3209). | Changing collections to paths later touches the P2.S3 dashboard. |
| D3218 | Task 6a details of D3201, D3203, D3204 and D3213: (a) `store.changed` is written by `OutboxStoreChangedHook` in `plugins/platform-outbox`, registered on tenancy's lifecycle registrar, through a new optional `TenantLifecycleHook.storeChanged` that the update, archive and subdomain use cases await inside their transaction (settings on every update, status on an archive that changes the status, domain on a real subdomain change); tenancy cannot import the outbox because the outbox already depends on tenancy. (b) The resolve payload carries all five D3203 fields (`description`, `showAddressField`, `soldOutBehavior`, `logoPath`, `direction`), built field by field so the new internal `channelId` of the row never leaves; the Valkey shape check is `storefrontStoreSchema` plus `logo === logoPath`, so pre-P3.S2 entries are re-read; a row whose language is not a platform language resolves to nothing. (c) The storefront context is a shop-API context on the store channel created **without** `req` (the tenant is anchored on that context only, never on the request Vendure's own `@Ctx()` shares); handlers use `@StorefrontScoped()` (guard + a filter answering 404 with an empty body) and `@StorefrontCtx()`; store and business status are read from the rows on each call (one indexed join, no cache). (d) The rate-limit resolver exposes `limitKeyOf(req, policy)`: a signed request whose `clientIp` is missing **or not an address** goes to `storefront-render` (6000/min, fails open) keyed `internal:<kid>`; `resolve()` prefers a valid signed `clientIp` for every caller. | No dependency cycle; one source for the public store shape (Task 4); the default request context must never carry a storefront tenant. | Moving the hook to `plugins/storefront-api` if the outbox should stay topic-agnostic. |
| D3219 | Task 6b details of D3205 and D3206: (a) the projection's outbox consumer and backfill read the catalog as the store through a new reviewed tenancy export `StorefrontStoreContexts.forStore(storeId)` (the same anchored context the storefront guard builds) and check the store belongs to the delivery's business; rows are written in the delivery's transaction. A row is built from the catalog's `landingPage` view (active and hidden, sold out or not, never a draft) found by the product's slug (`CatalogProductQueries.byId` then `CatalogReadService.findBySlug`); a rebuild walks `CatalogProductFactsReader.pageIds`. (b) The backfill is a `catchUpTask` every 15 minutes (`storefront-projection-backfill`) over active stores with no row, one transaction per store, instead of a bootstrap hook that every api instance and the migrate role would run. (c) Indexes are named explicitly and lead with `businessId` (`(businessId, storeId, productId)` and `(businessId, storeId, slug)` unique; `(businessId, storeId, listed, createdAt, productId)` and `(…, listed, price, productId)`), since every query is confined by `TenantRepository`; a save drops a stale row of another product holding the slug. (d) The collection filter passes the members as one array parameter (`productId = ANY(:ids)`), never a bind list; collection pages sort like lists (no hand order). (e) Every error of the controller answers an empty body with its status (404 for not found and a refused store, 500 logged by class name only), through one catch-all filter; the catalog reserves the product slug `search` (`STOREFRONT_RESERVED_PRODUCT_SLUGS`). (f) `GET /store/collections` answers `{items}` and `GET /store/collection/:slug` `{collection, products}` (new shared schemas). | A storefront context without a request is the only way to read the catalog as the store from a job (ADR 0002); a bootstrap hook would race across instances. | The tenancy export moves if contexts for jobs get a general home; a store whose language changes keeps old product names in its rows until each product changes or the store is rebuilt. |
| D3220 | Task 6c details of ADR 0014 Phase 1 and D3208: (a) `cod_normalize_for_search` mirrors `normalizeForSearch` step by step with IMMUTABLE built-ins (`normalize`, `lower` under the builtin `pg_c_utf8` collation, `translate`, `regexp_replace` with the shared `Cf` ranges, NFD then Latin combining marks removed) instead of wrapping `unaccent`: the TS side strips marks after NFD, and `unaccent`'s wider dictionary (punctuation, Greek, Cyrillic) would break parity; the extension stays installed. `searchText` is still written by the TS normaliser; the SQL function proves parity and serves later SQL-side backfills and the dashboard search. (b) One trigram index, `btree_gin` `("storeId", "searchText" gin_trgm_ops)` (declared `synchronize: false` on the entity), instead of a plain GIN plus a combined one, and no `to_tsvector('simple')` index: the exact-word and prefix ranks are computed on the rows the trigram filter returns. (c) The search runs through `TenantRepository`'s query builder (`tenantQuery`), so no raw-data allow-list entry is needed. (d) Ranking: rows matching the query itself before rows only a synonym finds, then exact word (2) or word prefix (1) plus `word_similarity`, newest on a tie; `sort` is ignored; no popularity boost until orders exist (P3.S3+). (e) Synonyms are symmetric `term`/`expansion` pairs per business (`storefront_search_synonym`), seeded with 40 Darija pairs on the business's first search (counted once per process; the unique pair index stops a concurrent second seed, which is logged and dropped); a query expands to at most 8 variants (the query, the whole query swapped, each word swapped). (f) Integration databases get the search schema by running the migration's own `up` after `synchronize` (its synonym table dropped first), in the shared storefront test kit. (g) The fixture gate measured locally: recall@5 0.967, MRR 1.000 (recall = expected ids in the top 5 over `min(expected, 5)`); the misses are Latin Darija spelling variants (`caftan` ↔ `kaftan`), which share only their Arabic synonym. | A parity table built from one rule per character class proves equality; ranking from the query first keeps synonyms from pushing out exact matches. | A Postgres or Node Unicode upgrade may split the normalisers on characters outside the table; a business that deletes every synonym is reseeded (merchant editing is later). |
| D3221 | Task 8 details of D3202, D3207 and D3211: (a) a root layout per store language (`app/%5Ft/[locale]/layout.tsx` with `<html lang dir>`) fails `next build` on Next 16.4.5: its root-param check matches the loader tree's static segment `%5Ft` against the route's `_t`, finds no pathname params and refuses every `generateStaticParams`. **Deviation (plan fallback):** `app/layout.tsx` stays the one root layout; `app/%5Ft/[locale]/layout.tsx` renders `<div lang dir>` on the server and keeps the client `StoreDocumentLang` so `<html lang dir>` follows after hydration; `app/not-found.tsx` (status 404 for `/_404`) stays. A store id that is not a snowflake, a locale that is not the store's language or a binding of another (store, host) gives no tenant and the soft 404 (`app/%5Ft/[locale]/not-found.tsx`, `noindex`). (c) The proxy refuses `/_t`, `/_404`, `/_internal` and `/api/internal` in any case after collapsing repeated slashes and decoding up to three times; a malformed `%` sequence is refused too. The matcher still skips `api/`, so `/api/internal` in its own case is gated by the edge rule and the route's HMAC (D3211). (d) `STOREFRONT_THEME` (`default` | `compact`, default when unset) is validated by the storefront env and passed by compose. | Next's encoded-folder bug leaves no way to put `<html lang>` on the server under `/_t` without renaming the tenant segment, which every later task consumes; the fallback is the one the plan names. | A brief `lang`/`dir` mismatch on `<html>` before hydration for French and English stores; moving to per-locale root layouts once Next matches encoded segments (or renaming `TENANT_ROUTE_SEGMENT`). |
| D3222 | Task 11 details of D3210 and D3211: (a) `StorefrontRevalidateConsumer` (outbox `product.changed`, `collection.changed`, `store.changed`) runs its deliveries on `catalog-effects`, the projection consumer's queue, and only queues a `storefront-revalidate` job (`srv-<storeId>-<outboxId>`, 2 s delay) with `product:<id>`/`collection:<id>` plus `store:<id>`, or `store:<id>` alone for a store change; the worker makes the signed `POST {STOREFRONT_INTERNAL_URL}/api/internal/revalidate` and then asks the coalescer for a purge of the store's hostnames (platform subdomain + custom domains). (b) A `store.changed` of the settings keeps the one-`UPDATE` relist and also queues a rebuild of the store's projection on a new bulk queue `storefront-projection` (`spr-<storeId>-<outboxId>`, run through `ProjectionBackfill.rebuild`, one transaction), because product names are read in the store language; the rebuild then queues a `store:<id>` revalidation. (c) `STOREFRONT_INTERNAL_URL` is optional in the api env (compose: `http://storefront:3001`); unset, revalidations are logged and succeed, and pages expire by their cache life; set, it needs `INTERNAL_HMAC_ACTIVE_KID`. `StorefrontApiPlugin.init({ platformDomain, storefront })` passes it; a bare registration (plugin tests) keeps the logging revalidator.
