Decisions taken while building phase P3. Each row gives the decision, why, and the cost if it proves wrong. Blocks: coordinator D3000–D3099, P3.S1 D3100–D3199, P3.S2 D3200–D3299, P3.S3 D3300–D3399, P3.S4 D3400–D3499, P3.S5 D3500–D3599.

| D3216 | Task 7 details of D3214: (a) a tag revalidation reads the index (`ZRANGE`) and then, in one `MULTI`, deletes those entries and `ZREM`s only those members (plus the expired-score prune), rather than deleting the whole index: an entry indexed between the read and the `MULTI` keeps its member, so the next revalidation still reaches it. (b) The 250 ms timeout wraps every handler command (`cache/command-timeout.ts`, a race; the command itself still completes) and the client also gets `socket.connectTimeout` 1 s and `commandsQueueMaxLength` 1000. (c) The memory guard polls lazily, at most every 30 s on the next entry write, instead of a background timer; reads and revalidations are never gated. | D3219 | Task 6b details of D3205 and D3206: (a) the projection's outbox consumer and backfill read the catalog as the store through a new reviewed tenancy export `StorefrontStoreContexts.forStore(storeId)` (the same anchored context the storefront guard builds) and check the store belongs to the delivery's business; rows are written in the delivery's transaction. A row is built from the catalog's `landingPage` view (active and hidden, sold out or not, never a draft) found by the product's slug (`CatalogProductQueries.byId` then `CatalogReadService.findBySlug`); a rebuild walks `CatalogProductFactsReader.pageIds`. (c) Indexes are named explicitly and lead with `businessId` (`(businessId, storeId, productId)` and `(businessId, storeId, slug)` unique; `(businessId, storeId, listed, createdAt, productId)` and `(…, listed, price, productId)`), since every query is confined by `TenantRepository`; a save drops a stale row of another product holding the slug. (d) The collection filter passes the members as one array parameter (`productId = ANY(:ids)`), never a bind list; collection pages sort like lists (no hand order). (e) Every error of the controller answers an empty body with its status (404 for not found and a refused store, 500 logged by class name only), through one catch-all filter; the catalog reserves the product slug `search` (`STOREFRONT_RESERVED_PRODUCT_SLUGS`). | D3220 | Task 6c details of ADR 0014 Phase 1 and D3208: (a) `cod_normalize_for_search` mirrors `normalizeForSearch` step by step with IMMUTABLE built-ins (`normalize`, `lower` under the builtin `pg_c_utf8` collation, `translate`, `regexp_replace` with the shared `Cf` ranges, NFD then Latin combining marks removed) instead of wrapping `unaccent`: the TS side strips marks after NFD, and `unaccent`'s wider dictionary (punctuation, Greek, Cyrillic) would break parity; the extension stays installed. `searchText` is still written by the TS normaliser; the SQL function proves parity and serves later SQL-side backfills and the dashboard search. (b) One trigram index, `btree_gin` `("storeId", "searchText" gin_trgm_ops)` (declared `synchronize: false` on the entity), instead of a plain GIN plus a combined one, and no `to_tsvector('simple')` index: the exact-word and prefix ranks are computed on the rows the trigram filter returns. (c) The search runs through `TenantRepository`'s query builder (`tenantQuery`), so no raw-data allow-list entry is needed. (d) Ranking: rows matching the query itself before rows only a synonym finds, then exact word (2) or word prefix (1) plus `word_similarity`, newest on a tie; `sort` is ignored; no popularity boost until orders exist (P3.S3+). (e) Synonyms are symmetric `term`/`expansion` pairs per business (`storefront_search_synonym`), seeded with 40 Darija pairs on the business's first search (counted once per process; the unique pair index stops a concurrent second seed, which is logged and dropped); a query expands to at most 8 variants (the query, the whole query swapped, each word swapped). (f) Integration databases get the search schema by running the migration's own `up` after `synchronize` (its synonym table dropped first), in the shared storefront test kit. (g) The fixture gate measured locally: recall@5 0.967, MRR 1.000 (recall = expected ids in the top 5 over `min(expected, 5)`); the misses are Latin Darija spelling variants (`caftan` ↔ `kaftan`), which share only their Arabic synonym. | A parity table built from one rule per character class proves equality; ranking from the query first keeps synonyms from pushing out exact matches. | A Postgres or Node Unicode upgrade may split the normalisers on characters outside the table; a business that deletes every synonym is reseeded (merchant editing is later). |
