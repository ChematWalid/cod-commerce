## activeQueues finding (ADR 0013 addendum)
**Prediction confirmed.** With `@vendure/job-queue-plugin` 3.8.1, `BullMQJobQueueStrategy` puts every Vendure queue into one BullMQ queue; a worker whose `activeQueues` excludes a queue still receives its jobs and **fails** them. Real output (`active-queues.e2e.test.ts`, `activeQueues: ['probe-critical']`, BullMQ 5.81.5, Valkey 8.1.11), written first as a plain test:

```
FAIL  |e2e| tests/e2e/active-queues.e2e.test.ts > worker activeQueues with the BullMQ job queue > a worker leaves jobs of inactive queues for another pool
AssertionError: expected 'failed' to be 'waiting' // Object.is equality
```

The job's `failedReason` is `No processor defined for the queue "probe-bulk"`. The desired behaviour stays as an `it.fails` test (an upstream fix turns it red), next to a "known limitation" test that asserts the failure.

**Decision: all queues on every worker.** `WORKER_ACTIVE_QUEUES` is empty in `.env.example` and compose; nothing sets `activeQueues` until P1.S6 (queue registry) chooses a pool split (own `JobQueueStrategy` per pool, an upstream change, or a Redis prefix per pool) and adds a boot assertion. The addendum is in [ADR 0013](../../adr/0013-process-model-job-queues-scheduler.md#addendum-2026-11-07-activequeues-with-vendures-bullmq-plugin); **the user accepted it as written on 2026-11-07.**

## Gotchas
- **Start data services by name.** A bare `docker compose up -d` now also builds the image and starts `migrate`, `api` (host port 3100) and `worker`. Use `docker compose up -d --wait postgres pgbouncer valkey garage mailpit`.
- **The Postgres healthcheck must use TCP** (`pg_isready -h 127.0.0.1 -p 5432 …`). Without `-h` it uses the unix socket, which also answers during the `docker-entrypoint` initdb temporary server (no TCP), so `service_healthy` fires early on a fresh volume and `migrate` gets `ECONNREFUSED` (seen on the clean-clone run).
- **A second `docker compose up -d` re-runs `migrate`** (the exited container starts again) and api/worker wait on it again; it is a no-op by design (`migrationsRun: []`, `seed.changes: []`).
- **Valkey must be up before api and worker start** (R3-7); compose handles the ordering, a host-run `dev` does not.
- **Parse `migrate` output by its JSON line** (`{"event":"migrate.done",…}`), never by the last line: framework and migration lines come first.
- **The root `pnpm build` already passes `--concurrency=1`;** adding it again (`pnpm build --concurrency=1`) makes turbo refuse the duplicate flag.
- **`verify-stack.sh` needs the root `.env`** (CI copies `.env.example`). It uses compose project `cod-verify` with ports +10000 and never touches project `cod`; the evidence script uses `cod-evidence` with ports +20000.
- **After an image rebuild, the first `up` is slow** (Docker unpacks the 1 GB image: 238 s against 66 s warm locally). A cold local build is 180–370 s.
- **e2e support:** an api test server and a worker cannot boot in one process (cron names are process-global); use separate files. `PostgresInitializer` forces `synchronize: true` unless subclassed.
- Part 2's gotchas still apply: one `@vendure/core@3.8.1` snapshot in the lockfile, `vendurePreset` for tests that import Vendure, turbo `passThroughEnv` for new variables, `onlyBuiltDependencies` for native builds, CI has no `.env` files.
