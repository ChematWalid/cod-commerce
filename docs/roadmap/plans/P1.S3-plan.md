# P1.S3 Permissions catalog & roles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A 93-permission catalog in 12 areas, 7 built-in roles per business, custom roles with None/View/Full per area, per-member store access, a `requirePermission` guard for later plugins, and an activity log.

**Architecture:** `packages/shared/src/permissions/` holds the catalog and the pure expansion rules. New plugin `plugins/rbac` stores business roles and member assignments in tenant tables and projects them onto Vendure Roles, so the stock `@Allow` check on the active channel enforces every permission. Tenancy gains a lifecycle registry so roles are seeded inside the provisioning transaction.

**Tech Stack:** Vendure 3.8.1, NestJS, `@nestjs/graphql` 14, TypeORM 0.3.31, Postgres 17, Valkey, React dashboard (Lingui), Vitest, Playwright.

**Spec:** `docs/roadmap/P1-foundation.md` section P1.S3; handoffs P1.S1 and P1.S2; ADRs 0002, 0008, 0016, 0017; `docs/research/dashboard-captures.md` "Team"; `docs/research/api-surface.md` "Team".

**Branch:** `feat/p1-s3-rbac` (from main at cf3f063) · **Issue:** #6

## Verified facts (Vendure 3.8.1 source; do not re-derive)

Paths are under `@vendure/core/dist` unless stated.

**Permissions and Roles**
- `Role.permissions` is `simple-array`, a Postgres `text` column (`entity/role/role.entity.js`, init migration). A Role has no limit on permission count. Names are comma-joined, so a name cannot hold a comma.
- `api/config/generate-permissions.js` makes every permission name a value of the GraphQL enum `Permission`, so a name must match `[_A-Za-z][_0-9A-Za-z]*`. `orders.cancel` is not a legal name.
- `RoleService.checkPermissionsAreValid` accepts assignable names only and always refuses `SuperAdmin`. `RoleService.create` and `update` require the caller to hold every granted permission on the target channels. They also add `Authenticated`. `ensureRolesHaveValidPermissions` strips removed names at boot.
- A Role has many channels, a User has many Roles. `getChannelPermissions` (`service/helpers/utils/get-user-channels-permissions.js`) gives each channel the union of the permissions of the user's Roles on that channel.
- The guard: `AuthGuard` → `RequestContextService.userHasRequiredPermissionsOnChannel` intersects `@Allow`'s names with `channelPermissions` of the **active** channel only. A channel absent from the session means no permission there.
- `ChannelService.create` assigns every new channel to the SuperAdmin and Customer roles (lines ~591-609).

**Session cache**
- `session.service.js` subscribes to TypeORM: `afterInsert`, `afterUpdate` or `afterRemove` of a `Role` or `Channel` **with `event.entity`** calls `sessionCacheStrategy.clear()` under a 50 ms race. `DefaultSessionCacheStrategy.clear` invalidates a tag covering **every session on the platform**.
- That clear runs **inside the transaction, before commit**, so a concurrent request can re-cache the old permissions.
- **Not cleared at all:**
  - `AdministratorService.assignRole` and `update({roleIds})` save `User.roles` only.
  - `ChannelService.assignToChannels` uses `relation().add()`, so no entity event fires.
  - `RoleService.update` that only changes channels leaves the Role subject without column changes (TypeORM `Subject.mustBeUpdated`).
- `serializeSession` writes `channelPermissions`; `cacheExpiry` is `sessionCacheTTL`, 300 s by default and unset in this repo. That is the bound on staleness if nothing invalidates.
- `TenantContextResolver` and `storeActorOf` read `ctx.session.user.channelPermissions`, so they see the same cached view.

**Stock resolvers**
- `createRole` needs `CreateAdministrator`; `updateRole` `UpdateAdministrator`; `deleteRole` `DeleteAdministrator`; `roles` and `administrators` `ReadAdministrator`.
- `createAdministrator`, `updateAdministrator` and `assignRoleToAdministrator` need `Create`/`UpdateAdministrator`. Stock `update` writes password and email directly.
- `channels` needs `ReadSettings` or `ReadChannel` and lists every store's token unscoped (A1). `createChannel`, `updateChannel` and `deleteChannel` allow `SuperAdmin` or the matching channel write. Seller writes need `Create`/`Update`/`DeleteSeller`. `updateGlobalSettings` needs `UpdateSettings` or `UpdateGlobalSettings`.

**EventBus** (`event-bus/event-bus.js`): `registerBlockingEventHandler` handlers run inside `publish` and are awaited, so a throw reaches the publisher and they share `event.ctx`'s transaction. `ofType` subscribers run only after the context's transactions finish.

**Dashboard** (`@vendure/dashboard/src`): `usePermissions().hasPermissions` reads the active channel's permissions from `me.channels`. `Dialog`, `Switch`, `RadioGroup`, `Accordion`, `Badge`, `Table`, `Tabs`, `Select`, `Textarea`, `AlertDialog` are exported. A P1.S2 finding: the stock stylesheet sets `direction: rtl` on every element, so LTR runs need the direction set inline.

**Repo**
- Tenancy's provisioner already gives the Owner role "every assignable plugin permission except `PLATFORM_ONLY_CUSTOM_PERMISSIONS`".
- `Business.ownerRoleId` holds its integer Vendure id; the role is `owner-<businessId>`, extended to each new store.
- `runMigrate` boots a worker after migrations and runs `seedPlatformDefaults`.
- CI's last main run: `others` 5.4 min, `auth-1` 6.5, `auth-2` 4.5, against a 10-minute limit.

|---|---|---|---|
| D52 | Catalog keys are dotted (`orders.cancel`). Each maps by one pure function to a Vendure name: `Cod` + PascalCase of the segments (`CodOrdersCancel`). | The GraphQL enum refuses dots and `simple-array` refuses commas. | Renaming names needs a role rewrite, which the converge in D57 does. |
| D53 | **Role mapping.** A `BusinessRole` has `role_binding` rows, each pointing at one Vendure Role. Scope `all`: one Vendure Role on **every** store channel of the business, extended when a store opens. Scope `<storeId>`: one Vendure Role on that channel. A member with "all stores" holds the `all` binding of each role; a member with "selected stores" holds one binding per role and store. Bindings are created on first use, Owner's at provisioning. A `selected` binding and its Vendure Role are deleted when its last holder leaves. Deleting a role removes all its bindings and Vendure Roles. Sharpens ADR 0002's "one role set per store" (addendum). | A store opening writes one row per `all` binding instead of one per member, the existing owner role is already an `all` binding, and unused pairs cost nothing. | A rewrite to one role per store: one migration over the binding rows. |
| D54 | `member_role_assignment` has one row per (member, role), each with `storeAccess` and `storeIds`. The API sets one store access for all of a member's roles, as the Invite dialog does. P1.S4 calls `MemberAccessService`. | Matches the research dialog; the row shape leaves room for per-role scope. | Add an API field. |
| D55 | **Invalidation.** Every use case that changes what a user can do (a) writes through `RoleService` and `AdministratorService` so core events fire, and (b) after commit deletes the cached sessions of every affected user and repeats the delete after `SESSION_REDELETE_DELAY_MS` (500 ms). Failures are logged; the bound is then `sessionCacheTTL` (300 s). Resolvers carry no `@Transaction`. | Core's clear is pre-commit, and absent for assignments and channel extensions. The second delete covers a reader that loaded before the commit, as P1.S1's host resolver does. | Core's platform-wide clear costs one session reload per active session per role write. Rate at Growth; bypass by writing through a query builder. |
| D56 | Tenancy gets `TenantLifecycleRegistry` with hooks `businessProvisioned` and `storeCreated`, awaited inside the provisioning or store transaction; a throw rolls it all back. Tenancy still creates the Vendure Owner role. RBAC's hook seeds the 7 rows, binds Owner to `business.ownerRoleId` and assigns the owner. | Tenancy cannot import rbac. A direct hook is simpler to reason about than an event for an atomic step. | Replace with a blocking event. |
| D57 | **Existing businesses.** No data migration in SQL (snowflake ids come from the generator). `runMigrate` calls `RbacConvergeService.convergeAll`: one transaction per business, reads first, writes only on a difference. It inserts missing built-ins, adopts `ownerRoleId` as Owner's `all` binding (same Vendure Role id, so sessions and user rows stay valid), creates the owner's assignment, re-extends every `all` binding to every store channel (idempotent; it repairs a store opened while a hook was absent), sets built-in permissions to the current template, then flushes the sessions of all holders of every changed role. It runs on every migrate, so a later catalog addition reaches Owner. | D14's pattern; the owner keeps access throughout because the role id never changes and permissions only grow. | A slow migrate with thousands of businesses: move to a fan-out job (ADR 0002 §4). |
| D58 | `requirePermission(key)` = `applyDecorators(Allow(name), TenantScoped())`, usable on resolvers and controllers. No guard of our own reads roles: Vendure's check on the active channel **is** the per-store check. | One enforcement path. A platform superadmin passes `@Allow` but has no tenant, so it fails closed. | Add a guard behind the same decorator. |
| D59 | **Stock permissions.** Merchant roles carry exactly one stock permission: `Authenticated`. Plugin grants come only from `ENGINE_GRANTS` (catalog key → plugin permission): `store.stores.view`→`ReadTenantStore`, `store.stores.create`→`CreateTenantStore`, `store.settings.edit`→`UpdateTenantStore`, `settings.business.view`→`ReadTenantBusiness`, `settings.business.edit`→`UpdateTenantBusiness`. Owner also keeps every other assignable plugin permission except the platform-only ones, exactly as today. A unit test fails if `ENGINE_GRANTS` holds any stock `Permission` value not on `REVIEWED_STOCK_ENGINE_GRANTS`, which is empty today. A later session that needs one, such as `ReadCatalog`, reviews that surface and adds it there. An allowlist, because a denylist misses whatever nobody thought of (`*ApiKey`, `*PaymentMethod`, and so on). | Carry-over from P1.S2: stock `updateAdministrator` writes password and email. `ReadSettings` lists every store's token. | One map entry per later grant. |
| D60 | **Escalation rules**, checked in `application` from our rows inside the lock, never from the session. A role's **reach** is every store it is bound to; an `all` binding reaches every store of the business. (1) A new or duplicated role has no bindings, so its permissions must be a subset of what the actor holds on the active store. (2) Editing or deleting a role needs the actor to reach it: `all` access, or every store in the role's reach within the actor's stores. Both the role's current and its new permissions must be held on **each** store in reach. (3) `setMemberAccess`: for each target store the actor must hold every permission of every role being added or removed; "all stores" also needs the actor to hold them with `all` access. (4) A target can be changed only if, on every store the target can access, the actor has access and holds the target's permissions there. (5) Nobody changes their own assignment. (6) Non-owners cannot edit a role they hold. (7) Only an Owner holder may grant or remove Owner. (8) The business's `ownerAdministratorId` keeps Owner always, and at least one holder must remain. | Vendure's own rule (grant only what you hold) is bypassed because we run `RoleService` as superadmin, so we must restate it. | Relax one predicate. |

## Review Focus

1. A member mid-session when their role loses a permission: the very next request is refused, not 300 s later. Tests prove it on one process; the eviction targets the session cache shared in Valkey, which the live evidence exercises with one api. Task 8.
2. A store opened after members were assigned: an "all stores" member can use it on the next request; a "selected" member still cannot. Task 7.
3. Role names that differ only by case, spacing or Arabic presentation forms: treated as the same name, in every path including Duplicate. Task 8.
4. Duplicate pressed twice, or concurrently: `(copy)` and `(copy 2)`, no 500. Task 8.
5. An archived store in a member's selected list: grants nothing, and does not satisfy "at least one store". Task 7.
