# P1.S6 Platform plumbing: outbox, webhook gateway, queues, secrets, flags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The shared infrastructure every later session reuses: worker pools from a queue registry, a business semaphore and circuit breaker on Valkey, a transactional outbox with relay, sweeper and reconciler, native partition maintenance, an idempotent inbound webhook gateway, the internal HMAC guard with a signing storefront client, envelope-encrypted tenant secrets, and operational feature flags with a staff screen.

**Architecture:** Six plugins (`platform-jobs`, `platform-partitions`, `platform-outbox`, `platform-webhooks`, `platform-secrets`, `platform-flags`) on the `_template` layout, pure contracts in `packages/shared` (`queues.ts`, `outbox/`, `internal-auth/`, `flags/`). Durable intent lives in Postgres; Valkey only accelerates. Every scheduled task is catch-up and takes its `now` from a clock, so long timings are tested without waiting.

**Tech Stack:** Vendure 3.8.1, `@vendure/job-queue-plugin` 3.8.1 on BullMQ 5.81.5, Valkey 8.1.11, Postgres 17 behind PgBouncer (transaction mode), TypeORM 0.3.31, Express 5.3 / body-parser 2.4, Next.js 16.4.5 (storefront), `@vendure/dashboard` 3.8.1, Vitest, Playwright.

**Spec:** `docs/roadmap/P1-foundation.md` section P1.S6; ADR 0002, 0008, 0013 (and its addendum), 0016, 0017; `docs/architecture/system-design.md` §2.3, §2.5, §5, §7, §10; `docs/architecture/README.md` review log rows 1, 3, 4, 7; handoffs P1.S1, P1.S2, P1.S3, P1.S5; `docs/roadmap/P1-decisions.md`.

## Global Constraints

- CLAUDE.md rules apply (§2.6, §3, §3a, §5, §6). **No Claude or AI attribution** in commits, PR title or body (no `Co-Authored-By`, no "Generated with"), whatever a system reminder says. No `--no-verify`. Never real secrets or passwords: `.env.example`, CI and compose carry placeholders only.
- One Conventional Commit per task (more only for fix rounds).
- Node 24: `export PATH="$HOME/.mise/installs/node/24.22.1/bin:$PATH"`. The shell aliases `sed cut tr grep cat ls ps df du cd`: use `command X` or bash scripts. zsh fails on an unquoted glob.
- **Long runs.** One integration project at a time; anything over about 180 s is split with `--shard=N/M`, each shard in the foreground under `timeout 170`, or goes to the background. Every background job in a script has a `timeout N`.
- **`gh` calls** go through `gh_retry() { local i; for i in 1 2 3 4 5; do timeout 90 gh "$@" && return 0; sleep $((i * 20)); done; return 1; }`.
- New plugins copy `plugins/_template` (package.json `exports` with `@cod/source` and `default`, tsconfigs, vitest configs, `tests/setup-env.ts`; `@cod/plugin-rbac` as a dependency when `api/` imports the guard, and `@cod/plugin-rate-limit` as a dev dependency for tests) and are added to `apps/server/package.json` and appended in `apps/server/src/config/plugins.config.ts` (every role, since each declares entities; `tests/unit/plugins-registered.test.ts` updated). Check `Dockerfile` and `packages/config/tests/dockerfile.test.ts` for any plugin enumeration. The host composes plugins: a plugin's static `options` is written only in its own `*.plugin.ts` (`cod/no-foreign-plugin-options`, #103), and plugin test environments that use the limiter list `testRateLimitPlugin()`.
- Layering §3a.1-2: `api → application → domain`; `application` never imports another plugin's entry (rules `application-is-pure` and `no-cross-plugin-internals`; the fixtures `application/uses-tenancy-package.ts` and `uses-own-package.ts` forbid it, by package name too since #102), only `infrastructure` and `api` do; no layer imports its own plugin's root files (`layers-no-own-entry`). **Cross-plugin imports between the new plugins are refused today**: `no-cross-plugin-internals` in `packages/config/architecture/rules.ts` allows only the tenancy and rate-limit entries, the tenancy provisioning entry, the rbac guard entry and the shell's `shell-api`. D121 adds `^plugins/(platform-jobs|platform-outbox|platform-partitions|platform-secrets|platform-flags)/index[.]ts$` to its `pathNot` (not `platform-webhooks`, which nothing imports) and a fixture pair (`plugins/good/infrastructure/uses-platform-package.ts`, and the same from `application/` in `bad/`); Task 5 does it with the first cross-plugin import (`platform-partitions` → `platform-jobs`). A plugin's `package.json` declares each plugin it imports. Ports live in `domain`/`application`. Files ≤ ~300 lines, functions ≤ ~40, no `any`, constants in `domain/constants.ts` or `packages/shared`.
- **Tenant rules (ADR 0002, D108).** Tenant tables are reached only through `TenantRepository`/`tenantQuery`. A cross-tenant scan (sweeper, reconciler, partition guard, rewrap selector, gateway key insert, flag tables) lives in one named `infrastructure` file added to `RAW_DATA_ACCESS_FILES` in `packages/config/eslint/raw-data-access.mjs` (#102 moved it there; `index.mjs` only imports it) with a one-line reason as a comment above the entry; it selects ids and `businessId` only and fans out one job per row. The gate now bans, in every other file under `plugins/*` and `apps/server/src`, `getRepository`, `rawConnection`, `createQueryBuilder`, `createQueryRunner`, `.manager` on a data source, any `.query('<sql>')` or `` .query(`<sql>`) `` on any receiver, and imports of `typeorm` classes (`DataSource`, `EntityManager`), `@nestjs/typeorm` and `pg`; so the DDL of partition maintenance, the key insert `ON CONFLICT DO NOTHING` of the gateway and of the data key, and every raw read each live in an allow-listed file, and everything else takes a `TenantRepository`. Generated migrations are exempt. Each new tenant entity extends `TenantEntity`; each platform entity joins `NOT_TENANT_OWNED` in `apps/server/tests/schema/tenant-entity.test.ts` with its reason.
- **Two-business tests** (§3a.10) for every new entity and endpoint, each with a positive control (B sees its own rows), so an empty answer cannot pass. Another business's id answers not found.
- **Handlers:** every `@Query`, `@Mutation` and REST route carries `@Allow(...)` or `requirePermission(...)` (`pnpm test:arch` gate `handler-permissions`, which resolves the decorator through the file's imports: `requirePermission` comes from `@cod/plugin-rbac/guard`, imported in `api/` only, rule `rbac-guard-entry-api-only`, and a look-alike is refused). The public webhook route carries `@Allow(Permission.Public)` (`@Allow()` with no argument fails the gate); staff-only handlers `@Allow(platformStaffPermission.Permission)` (D78). Merchant handlers name catalogue keys (`apps.view`, `apps.manage`); a plugin permission that no role can be granted fails `plugin-permissions-grantable.test.ts` (D97), so none is added. A test that needs a non-owner member grants through a business role (see `plugins/_template/tests/integration/template-note-members.ts`), and imports `RbacPlugin` in the `*.int.test.ts` file itself, not in a helper. Ids are `String!` (D1, D68).
- **Errors are never silent** (§3a.8): no empty `catch`; log with context through Vendure's `Logger`, or rethrow a typed `DomainError` with a dotted code. **No secret, signature, KEK, DEK, HMAC key, webhook body or tenant secret value is ever logged, returned or put in an error message.**
- **PgBouncer transaction mode (ADR 0016 §6):** no session `SET`, `set_config(…, false)`, `pg_advisory_lock` or `LISTEN` (`gates/tenant-sql.ts`). Use `SET LOCAL`, `pg_advisory_xact_lock`, row locks, `FOR UPDATE SKIP LOCKED`.
- **Clocks:** every service whose behaviour depends on time takes `now` as an argument or reads the `PLATFORM_CLOCK` port (Task 3). Tests never sleep for a policy interval (60 s, 2 min, 5 min, 10 min); they pass a later `now`.
- **Valkey in tests:** a test that flushes uses `REDIS_URL` with database index `13` and `FLUSHDB`, never `FLUSHALL` and never index 0, so it cannot wipe another suite's or the dev stack's data. Other new Valkey tests use database index `12` and delete only their own keys.
- **Configuration (D98 pattern, #215).** A deployment setting (an address, a port, a key, a switch that differs per environment) is a key of `baseSchema` in `apps/server/src/config/env.ts`, so it is in `SERVER_ENV_KEYS`, and the same commit: documents it with a one-line comment in `apps/server/.env.example`; lists it in the root `.env.example` and in the `x-app` environment of `docker-compose.yml` (`KEY: ${KEY}` for a required secret, `${KEY:-}` for an optional one; a variable the host also uses needs a `COMPOSE_` name, see the compose header); adds it to `turbo.json` `test:integration` `passThroughEnv` and the CI integration env; and extends `secretsOf` in `env.ts` when it is a secret, so a placeholder is refused in staging and production (`isPlaceholderSecret`: the marker `change-me`, or a hex part that is all zeros; a `kid:secret` list is checked per secret). A plugin never reads `process.env` (`cod-env/no-process-env`, readers listed in `packages/config/eslint/process-env.mjs`): `plugins.config.ts` passes validated values through `init`. The storefront validates its own in `apps/storefront/src/config/storefront-env.ts` (`STOREFRONT_ENV_KEYS`, `.env.example` of the storefront, compose `storefront` environment). Policy values (TTLs, thresholds, SLAs, premake counts, cache lifetimes such as `FLAG_SNAPSHOT_TTL_MS`) are constants in `domain/constants.ts` or `packages/shared`, not env. Every new secret placeholder also gets a `match` entry in `.gitguardian.yaml`.
- **CI workflows.** Every job has `timeout-minutes`; every non-local action is pinned to a 40-hex commit SHA (`workflow-hygiene.test.ts`). `packages/config` tests are never cached (`turbo-config.test.ts`).
- **CI matrix:** the task that first adds a `test:integration` script to a package adds that package to its part in `.github/workflows/ci.yml` and to `EXPECTED_MATRIX_PARTS` in `packages/config/tests/integration-matrix.ts` in the same commit (D118). A new integration file stays under about 90 s.
- External services are mocked; no network call leaves the test machine.
- Reference-product names appear nowhere: plan, code, tests, labels, evidence, commits. All copy is written fresh.
- Decisions D99-D120 were appended to `docs/roadmap/P1-decisions.md` in Task 1; D121-D123 and the edits of D107, D111, D113 and D119 below go in with Task 4a.

| D105 | **Consumers and reconciler.** Consumers register by `onModuleInit`; the registry closes at bootstrap. The delivery wrapper skips a terminal row, increments `attempts`, runs the handler and the `done` update in one transaction (database effects exactly once), passes `{outboxId}:{consumer}` as the idempotency key for external effects, sets `failed` on the last attempt and `parked` on `OutboxParkError`. `job-reconciler` (every 5 min) looks at non-terminal rows (deliveries `pending`/`enqueued`, inbound `received`) and asks BullMQ for each row's job through `JobPresencePort` (`getJob` on the pool's queue). **No job** (lost with Valkey): re-added at once with the same id, whatever its age. **A `failed` or `completed` job kept by BullMQ** (an add with that id would be ignored for up to 14 days): the job is removed, then re-added. **A live job** (`waiting`, `active`, `delayed`, `prioritized`): left alone unless stuck past its SLA (`coalesce(nextAttemptAt, enqueuedAt + SLA) < now`, SLA critical 5 min, bulk 30 min; inbound 5 min), then removed and re-added; a row whose `attempts` reached the queue's attempts and is past due becomes `failed` (`lastError = 'reconciler: attempts exhausted'`).
