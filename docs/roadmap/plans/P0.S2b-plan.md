# P0.S2b "Workspace scaffolding" (parts 1–6): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a runnable skeleton that follows the accepted ADRs and that every later session builds on. It contains:
- a pnpm workspace whose quality gates fail CI;
- the data services: Postgres 17, PgBouncer, Valkey, Garage and Mailpit;
- Vendure 3.8.1 with three roles (`api`, `worker`, `migrate`), health endpoints and an idempotent seed;
- one image with a role entry point;
- the dashboard host with Arabic RTL;
- a Next.js 16 storefront that resolves the store from the host;
- `plugins/_template`, the reference for CLAUDE.md §3a;
- real CI within the ADR 0001 budget.

**Architecture:** the layout follows ADR 0001: `apps/server`, `apps/storefront`, `packages/{shared,config,testing}` and `plugins/*`. `@vendure/*` is pinned and never patched.
- **Plugins:** every feature is a plugin with `domain/ application/ infrastructure/ api/ dashboard/ tests/`. Two independent checks enforce the layers: ESLint (`eslint-plugin-boundaries` plus `no-restricted-imports`) and a dependency-cruiser architecture test.
- **Package resolution:** workspace packages resolve to their source in dev and test (export condition `@cod/source`) and to `dist` in builds and at runtime.
- **Compose:** one compose file serves both as the local stack and as the single-VPS minimum (ADR 0011). One image runs every role, chosen by `ROLE` (ADR 0013).
- **Database URLs:** `api` and `worker` go through PgBouncer; `migrate` connects directly (ADR 0016 §6).
- **Storefront:** it resolves the store from `Host` and rewrites to `/_t/{storeId}/{locale}/…` (ADR 0005/0006). Its shared Redis cache handler keys entries by deployment id.

**Tech Stack:** Node 24.22.1, pnpm 10.34.9, TypeScript 5.9.3, turbo, ESLint 9 flat config, dependency-cruiser, Vitest 5 with SWC, Vendure 3.8.1 with BullMQ on Valkey 8.1, Postgres 17 with PgBouncer 1.26 in transaction mode, Garage v2.5.0 (S3), Mailpit, Next.js 16.4.5 with React 19.3, `@vendure/dashboard` on Vite 7.3.7, `playwright-core` 1.65.0, GitHub Actions.

## Global Constraints

- **CLAUDE.md rules apply (incl. §3a Engineering principles).**
- **No AI attribution:** no co-author trailer and no "generated with" line, in commits, PR titles or PR bodies. CLAUDE.md §4 overrides any harness default. `.githooks/commit-msg` and the `attribution-check` job enforce this.
- **Git:** never `--no-verify`, never push to `main`, never force-push. Make one Conventional Commit per task step, with the messages given below. Each commit builds and passes its tests.
- **Working agreement (user, 2026-11-07):** the agent squash-merges its own PR once CI is green. Anything that is the user's decision is asked as a multiple-choice question, including accepting an ADR addendum.
- **Mandatory command prelude.** Every command block in this plan starts with it, and every agent command runs it too. Shell state does not persist between tool calls, so each block re-runs the whole prelude.
  ```bash
  export PATH="$HOME/.mise/installs/node/24.22.1/bin:$PATH"; export COREPACK_ENABLE_DOWNLOAD_PROMPT=0
  SCRATCH="$HOME/scratch/p0s2b"; mkdir -p "$SCRATCH"; cd /mnt/drive3/Coding/commerce/cod-commerce
  ```
  - pnpm runs **only from the repo root**, and only after `packageManager` is set. Use `pnpm --filter …` to target one package.
  - Task 1 installs pnpm with `corepack enable --install-directory "$HOME/.local/bin" pnpm`. If that fails, use `npx -y pnpm@10.34.9 …`.
- **Shell:** zsh aliases shadow `sed`, `cut`, `tr`, `grep`, `cat` and `ls`, so commands use `command <tool>` or bash scripts.
  - **Never `pkill -f`.**
  - Start a server in its own process group: `setsid <cmd> > "$SCRATCH/<name>.log" 2>&1 & echo $! > "$SCRATCH/<name>.pid"`.
  - Stop it with `kill -- -"$(command cat "$SCRATCH/<name>.pid")"`.
  - Before any `curl` or test against a server, run `source scripts/lib/wait-http.sh; wait_http <code> <url> <timeout-s>` (the helper is created in Task 2).
- **Scripts:** run `chmod +x` right after writing each script. Commit scripts with LF line endings and the exec bit.
- **Memory:** about 4.8 GB of RAM is free.
  - Run builds **one at a time**; never run `next build` alongside the dashboard build.
  - Build with `NODE_OPTIONS=--max-old-space-size=2048`.
  - Any turbo or recursive pnpm build uses `--concurrency=1` or `2`.
- **Secrets:** none are needed and none are handled.
  - `.env.example` holds only syntactically valid placeholders. Each one carries the marker `change-me`, except the hex-only values, whose placeholder is all zeros.
  - `loadEnv` rejects both kinds of placeholder when `APP_ENV` is `staging` or `production`.
  - CI uses no secrets.
- **Git setup:** identity and hooks are already configured (`core.hooksPath .githooks`), and `gh` has admin and workflow scope.
- **Branding:** use ADR 0007's neutral copy. The branding gate (Task 3) checks `apps/`, `plugins/` and `packages/shared`.
- **Pins:** every dependency is pinned exactly (no `^` or `~`). Every image is pinned by tag and digest, and every action by SHA.

### Conventions shared by all tasks

- **Package format:** every workspace package is CommonJS (no `"type": "module"`).
- **Package exports:** a package that gets built declares `"exports": { ".": { "@cod/source": "./<entry>.ts", "default": "./dist/<entry>.js" } }`.
  - Plugins export only `"."`.
  - `@cod/config` is never built. Its exports point straight at source (`.mjs` and `.ts` files), and only Vitest and ESLint consume it.
- **tsconfig:**
  - `tsconfig.json` (typecheck and lint) includes `**/*.ts` and `**/*.mts`, excludes `dist`, and inherits `customConditions: ["@cod/source"]`.
  - `tsconfig.build.json` sets `"customConditions": []` and the correct `rootDir` (`src` for `packages/*`, `.` for plugins), so a build reads its siblings' `dist`. Turbo's `^build` builds the siblings first.
  - Vitest sets `resolve.conditions: ['@cod/source', ...defaultClientConditions]` and `ssr.resolve.conditions: ['@cod/source', ...defaultServerConditions]` (both exported by `vite`). The node environment reads only the SSR list, and each list replaces Vite's defaults, so the defaults are appended. Host-run Node dev scripts pass `--conditions=@cod/source`.
  - Never set `module: commonjs`. The base is NodeNext, which emits CJS for CJS packages.
- **Decorated constructors:** a constructor parameter typed with an interface uses `import type`. `isolatedModules` together with `emitDecoratorMetadata` would otherwise emit a runtime reference to the interface.
- **Test names:** each package keeps its tests in `tests/`.

  | Suffix | Kind | Runs in |
  |---|---|---|
  | `*.test.ts` | unit | `pnpm test` |
  | `*.int.test.ts` | integration (Postgres or Valkey) | `pnpm test:integration` |
  | `*.e2e.test.ts` | server end-to-end | `pnpm test:integration` |
  | `*.browser.test.ts`, `*.smoke.test.ts` | needs a running app | their own scripts |

  Vitest configs set `test.env: { TZ: 'UTC' }`.
- **Ports.** Every published port binds to a `*_BIND_ADDR` that **defaults to `127.0.0.1`**.

  | What | Port |
  |---|---|
  | api, inside containers | 3000 |
  | api, host-run dev and compose publish | **3100** (`API_PORT=3100`, `API_HOST_PORT=3100`; 3000 is taken on the dev machine) |
  | dashboard | `http://localhost:3100/dashboard` (Vite dev server: 5173) |
  | storefront | 3001 |
  | worker health | 3020 |
  | Postgres | 5433 |
  | PgBouncer | 6432 |
  | Valkey | 6380 |
  | Garage S3 | 3900 |
  | Mailpit SMTP / UI | **1026 / 8026** |

- **Server constants:** `apps/server/src/config/ports.ts` defines `DEFAULT_API_PORT = 3000`, `DEFAULT_WORKER_HEALTH_PORT = 3020` and `DEV_API_PORT = 3100`.
- **Placeholder values**, used in the root `.env.example`, `apps/server/.env.example`, CI env and the compose `x-app` block:

  | Key | Placeholder |
  |---|---|
  | `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `cod` / `change-me-pg` / `cod` |
  | `COOKIE_SECRET` | `change-me-` followed by 54 hex characters (64 characters in total) |
  | `SUPERADMIN_USERNAME` / `SUPERADMIN_PASSWORD` | `superadmin` / `change-me-admin` |
  | `S3_ACCESS_KEY` | `GK` followed by 24 zeros |
  | `S3_SECRET_KEY` | 64 zeros |
  | `GARAGE_RPC_SECRET` | 64 zeros |
  | `GARAGE_ADMIN_TOKEN` | `change-me-garage-admin` |
  | `APP_ENV` | `development` |
  | `CORS_ORIGINS` | empty (optional; default `[]`) |

### Deviations from the brief

Each deviation is recorded in the handoff of the part that makes it (CLAUDE.md §3a.12).

1. **Storefront port:** the acceptance URL `http://demo.localhost:3000` becomes **`http://demo.localhost:3001`**. ADR 0013 puts the api on 3000 and the storefront on 3001, and 3000 is taken on the dev machine.
2. **Object storage is Garage, not MinIO** (user decision 2026-11-07; ADR 0011 addendum, Task 2).
3. **The rewrite target carries the locale:** `/_t/{storeId}/{locale}/…`, using the store's default locale (ADR 0005/0006). Prefix negotiation stays in P3.S2.
4. **The `activeQueues` acceptance item:** the test documents the stock strategy's limitation instead of proving pool filtering (Task 10; ADR 0013 addendum if confirmed). Every worker runs all queues at Launch.
5. **`bullmq` is pinned to `5.81.5`.** The job-queue plugin declares only a peer range, so there is no "shipped" version to copy.
6. **Tenancy before P1.S1:** the template entity declares `businessId` itself and filters every query by it, and one channel stands for one business. P1.S1 replaces the three stubs.
7. **Ids:** an `IdGeneratorPort` with a 63-bit random placeholder. The ADR 0003 snowflake generator belongs to P1.S1.
8. **Feature gate:** `requireFeature(feature, scope)` takes a tenant scope, and `registerFeatureGate` comes with it, so P9.S1 changes no call site.
9. **Deferred:**
   - `@vendure/telemetry-plugin` → the observability session;
   - SIGTERM draining and the "draining" and "BullMQ connected" readiness checks → P3.S5;
   - ADR 0013 per-container memory limits → P3.S5;
   - the ADR 0006 D4 cache rules (TTL policy ≤ 6 h beyond the safety cap below, 512 KB entry limit, writes-off switch, gzip, in-process LRU) → P3.S5;
   - a node-local api check in the storefront `/readyz` → P3.S5.
10. **`DzdMoneyStrategy`** lives in `apps/server/src/config/` until P2.S4.
11. **Generated migrations** (`apps/server/src/migrations/**`) are exempt from `max-lines` and `max-lines-per-function`, and Prettier ignores them.
12. **Dashboard:** it stays at `/dashboard` in P0 (it moves to the root in P3.S5), and it has no `.po` catalogues yet (P1.S5).
13. **No PgBouncer in CI.** The `integration` job points both database URLs at Postgres. `scripts/verify-stack.sh` (the `stack` CI job) proves the pooled path.
14. **`GlobalSettings.availableLanguages` is seeded here**, not in P1.S1 as ADR 0002 says.
15. **Storefront `/readyz`** returns 200 when Redis is down and reports `checks.redis.ok: false` (ADR 0006 §12: the cache degrades to a miss).
16. **`@cod/shared` gains `src/platform/`** for platform defaults (money precision, currency, languages), the database-URL parser and the health response type. These are pure contracts that the server, storefront and testing packages share.

## Review Focus

The five failure modes most likely to bite. Each has a test in the task that owns it.

| # | Failure mode | Test (owning task) |
|---|---|---|
| RF1 | **Vacuous isolation test.** Vendure's fallback to the default channel would let "A cannot see B" pass even when the two scopes are the same business, or both empty. | Task 18: "rejects an unknown channel token instead of falling back to the default channel" and "A and B are two businesses, neither of them the default channel". |
| RF2 | **A lint glob or ignore silently skips `plugins/*`.** | Task 1: "lints every layer of a plugin". For every layer under `plugins/__lint_fixture__/…` (`.tsx` included), `isPathIgnored === false` and `max-lines` is configured. Task 18 repeats the check on the real `plugins/_template` files. |
| RF3 | **Host header edge cases:** a port, uppercase letters or a trailing dot; a spoofed `x-forwarded-host`. | Task 16: the proxy test `DEMO.localhost.:3001` → `/_t/demo/ar`, and the smoke test `Host: nope.localhost` + `X-Forwarded-Host: demo.localhost` → 404 through `next start`. |
| RF4 | **Schema drift between the migrations and the entities**, for every role's entity set. | Task 9: after `runMigrate` on an empty database, the schema builder for both the `migrate` and the `api` config reports `upQueries.length === 0`. Task 18 re-runs it with the template entity. |
| RF5 | **URL-reserved characters in DB passwords.** Compose interpolates them into the database URLs without encoding. | Task 5: the env test "rejects a database URL that a reserved character in the password broke". Task 12: the `verify-stack.sh --bad-password` variant. |

### Task 16: `apps/storefront`, a host-resolved hello page with the shared cache handler

**Decisions:**
- **Rewrite target:** `/_t/{storeId}/{locale}{path}`, using the store's `defaultLocale`.
- **Not-found handling:**
  - unknown hosts, disabled stores and public internal paths rewrite to `/_404`;
  - `app/%5F404/page.tsx` calls `notFound()`, so `not-found.tsx` renders with status 404;
  - `/_t`, `/%5Ft`, `/_404` and `/_internal` are blocked publicly, in any letter case.
- **Only `Host` is read.** `x-forwarded-host` is ignored.
- **The proxy matcher excludes** `api/`, `livez`, `readyz`, `_next/static`, `_next/image` and `favicon.ico`.
- **Cache handler:**
  - written in TypeScript and compiled to CJS (`cache/*.ts` → `cache/dist/*.js`), using erasable syntax only;
  - **source:** `~/scratch/p0s2a3/spike-f/app/handlers/next-example-dpl/{isr,use-cache}.js`;
  - `cache/NOTICE.md` records the upstream Next.js repo example path and the version tag it came from (read both from the spike files' headers or the P0.S2a-3 handoff), the MIT licence, and our changes.
- **Keys:**
  - entries are `next:{deploymentId}:isr:{key}` and `next:{deploymentId}:uc:{key}`;
  - tag indexes are **not** prefixed: `next:tag:{tag}` and `next:uc-tag:{tag}`.
- **TTL now:** every entry and every tag-index key gets `EX ≤ CACHE_ENTRY_MAX_TTL_SECONDS = 21_600` (6 h), so a `noeviction` Valkey cannot fill up. The rest of ADR 0006 D4 is deferred (deviation 9).
- **Testability:** factories over a `CacheRedisClient` port, so tests can use a fake.
- **`/readyz`** always returns 200. It reports `checks.redis.ok` as a `HealthProbeResponse` (deviation 15).
- **Locales:** the store locale is validated at runtime against `PLATFORM_LANGUAGE_CODES` (`@cod/shared`).

## Appendix A: ADR 0011 addendum text

> Append to `docs/adr/0011-hosting-and-regions.md` (Task 2, Step 7) as `## Addendum (2026-11-07): Garage replaces MinIO`.

**Decision (user, 2026-11-07).** Private objects are stored in **Garage** (Deuxfleurs; S3-compatible, self-hosted), not in MinIO. This covers exports, documents and labels, imports, and `archive/`. It changes Decision 2 ("S3-compatible storage (MinIO)"); everything else in this ADR stays as it is. MinIO is dropped everywhere: in dev, CI and production.

**Why.**
- **MinIO can no longer be pulled.** On 2026-11-07, `docker manifest inspect minio/minio:<tag>` answered `denied: requested access to the resource is denied`, and quay.io has no current tags. Running MinIO would mean building it from source or buying a third-party image.
- **Garage is actively maintained.** v2.5.0 is current on Docker Hub as `dxflrs/garage`. It is designed for self-hosting on small, heterogeneous nodes across sites. That matches both the single-Algerian-VPS minimum and the second-provider requirement.

**How it runs (P0.S2b).**
- **Image and config:** `dxflrs/garage:v2.5.0`, pinned by digest; `replication_factor = 1`; `db_engine = "sqlite"`; the S3 API on port 3900; `s3_region = "garage"`; path-style addressing.
- **Secrets and data:** secrets come from env (`GARAGE_RPC_SECRET`, `GARAGE_ADMIN_TOKEN`). Data and metadata live on named volumes.
- **First boot:** `garage server --single-node --default-bucket` creates the layout, the app key (`GARAGE_DEFAULT_ACCESS_KEY`/`_SECRET_KEY`) and the private bucket. It is idempotent across restarts (verified on 2026-11-07).
- **App settings:** `S3_ENDPOINT`, `S3_ACCESS_KEY` (`GK` + 24 hex), `S3_SECRET_KEY` (64 hex), `S3_BUCKET_PRIVATE`, `S3_REGION=garage`, `S3_FORCE_PATH_STYLE=true`.
- **Verified** with `@aws-sdk/client-s3` 3.1164.0 and the default checksum settings: PUT, GET and a presigned GET return 200; an anonymous GET returns 403.

**Features we rely on**

| Need | Garage v2.5.0 | Source |
|---|---|---|
| Presigned URLs | **Supported** | [S3 compatibility](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/); trial 2026-11-07 |
| Multipart upload | **Supported** | same page |
| CORS | **Supported** | same page |
| Path-style and vhost-style | **Supported**; we use path-style | same page |
| SSE-C | **Supported**; bucket-default encryption is **not** | same page |
| Bucket policies | **Not supported** | same page |
| ACLs | **Not supported** | same page |
| Object lock | **Not supported** | same page |
| Versioning | **Not supported** | same page |
| Lifecycle rules | **Partial**: only `Expiration` and `AbortIncompleteMultipartUpload`, with the prefix inside `Filter` | same page |

**Consequences.**
- **Access control is per key and per bucket,** not through policies or ACLs. Buckets are private by default.
  - Prefix-level rules (for example, per-tenant prefixes) are enforced in our code and when we issue presigned URLs.
  - Least privilege means one key per bucket and per role, set up in P3.S5. P0 uses a single app key with `RWO` on the private bucket.
- **Retention:** use lifecycle `Expiration` with a `Filter` prefix, or delete in our own code. Set `AbortIncompleteMultipartUpload` on the private bucket (P3.S5).
- **No object lock and no versioning.** A deleted or overwritten object is gone from every replica. Backups that must survive ransomware or operator error therefore rely on the second provider's controls: pgBackRest writes to a repository there, or copies are pulled from there using credentials the primary does not hold. This is decided in P3.S5.
- **Growth:**
  - Garage places each copy in a **different zone**. The recommended minimum is 3 nodes, and usable capacity is bounded by the smallest zone ([real-world cookbook](https://garagehq.deuxfleurs.fr/documentation/cookbook/real-world/)).
  - Every node must reach every other node on the RPC port, either over public IPv6 or over a mesh VPN.
  - Replication is not a backup.
  - Leaving the single-node layout means dropping `--single-node` and running `layout assign` and `apply` by hand.
  - Changing `replication_factor` on a live cluster has **not been verified**; the P3.S5 runbook tests it on staging.
- **Manual setup.** This runbook, from `--help` of v2.5.0, is also the Task 2 fallback:
  ```bash
  garage status
  garage layout assign -z <zone> -c <capacity> <node-id>
  garage layout apply --version <n+1>
  garage key import -n cod-app --yes <GK…> <secret>
  garage bucket create cod-private
  garage bucket allow --read --write --owner cod-private --key cod-app
  ```
- **Consistency:** the default `consistency_mode = "consistent"` gives read-after-write. Keep it.
- **Upgrades:** pin by digest, and read the Garage release notes on each bump, as for Vendure in M.S1.

## Appendix B: ADR 0013 addendum text

> Append to `docs/adr/0013-process-model-job-queues-scheduler.md` (Task 10, Step 6) as `## Addendum (2026-11-07): activeQueues with Vendure's BullMQ plugin`. Do this **only if `active-queues.e2e.test.ts` confirms the finding**, and replace the Evidence placeholder with the real output.

**Finding.** In `@vendure/job-queue-plugin` 3.8.1:
- `BullMQJobQueueStrategy` puts every Vendure queue into one BullMQ queue (`<prefix>:vendure-job-queue`), with the job name set to the Vendure queue name.
- A worker creates a BullMQ `Worker` on that queue as soon as any one of its queues starts.
- Its processor then looks up the job name among the queues **this** process started. For a job of a queue that `jobQueueOptions.activeQueues` excludes, it throws `No processor defined for the queue "<name>"`.

The job therefore **fails** and uses up an attempt. It is not left waiting for a worker of another pool.

**Evidence (P0.S2b-3, Task 10).** *[Run date, then the real Vitest output: `a worker processes jobs of its active queue` ✓ (`completed`); `a worker leaves jobs of inactive queues for another pool` as `it.fails` ✓; `known limitation: stock BullMQ strategy fails jobs of inactive queues` ✓, with the `failed` state and the `failedReason` exactly as printed.]*

**Decision.**
1. **At Launch, every worker runs all queues.** `WORKER_ACTIVE_QUEUES` stays empty. The desired-behaviour test stays as `it.fails`, so an upstream fix shows up as a failing test.
2. **The critical/bulk pool split belongs to P1.S6** (queue registry). The options to evaluate:
   - (a) a `JobQueueStrategy` that gives each pool its own BullMQ queue;
   - (b) an upstream change that keeps jobs of inactive queues waiting;
   - (c) a separate Redis prefix per pool.

   The selection criteria: no lost or failed jobs, a working dashboard job list, and unchanged semaphore and priority rules.
3. **Until P1.S6, nothing may set `activeQueues`.** P1.S6 adds a boot assertion that fails fast when `WORKER_ACTIVE_QUEUES` is non-empty while the stock strategy is in use.
