# P1.S2 Accounts & auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merchants register through a 3-step wizard that creates User + Business + Store atomically, log in and out, verify email (link + OTP), reset and change password and email, and manage profile and security, with OAuth behind a flag.

**Architecture:** New plugins `plugins/auth` (accounts, tokens, email flows, dashboard pages) and `plugins/rate-limit` (Valkey token buckets, used by auth and tenancy). Sessions stay Vendure's. Four stock Admin API mutations are shadowed by plugin resolvers so the stock dashboard pages keep working over our rules. Public pages are `authenticated: false` dashboard routes.

**Tech Stack:** Vendure 3.8.1, NestJS, `@nestjs/graphql` 14, TypeORM 0.3.31, Postgres 17, Valkey (ioredis 5.11.1), BullMQ, nodemailer, Mailpit, React dashboard (Lingui), Vitest, Playwright.

**Spec:** `docs/roadmap/P1-foundation.md` section P1.S2; `docs/roadmap/handoff/P1.S1.md`; ADRs 0002, 0008, 0010, 0012, 0017; `docs/research/second-pass.md` "Onboarding (new account)".

## Verified facts (Vendure 3.8.1 source; do not re-derive)

Paths are under `@vendure/core/dist` or `@vendure/dashboard/src`.

**Unauthenticated routes**
- `lib/framework/page/use-extended-router.tsx`: an extension route with `authenticated: false` is added at the router root with no app shell. A path already at the root is **skipped with only a dev warning**.
- `app/routes/` already has root routes `login`, `forgot-password`, `reset-password`. So a plugin **cannot replace** those three. Stock `login-form.tsx` links to `/forgot-password`; stock `reset-password.tsx` takes `?token=` and then runs `auth.login`.
- Login extension points are only `login.logo`, `login.beforeForm`, `login.afterForm` (`types/login.ts`). `registerLoginExtensions` shallow-merges, so auth's `afterForm` coexists with merchant-shell's `logo` and `beforeForm`. `afterForm` renders **inside the `<form>`**: its buttons must be `type="button"`.
- Stock `/profile` exists (`_authenticated/_profile/profile.tsx`) and the user menu links to it. It posts `updateActiveAdministrator` with `emailAddress` always and `password` when filled, and uploads via `setActiveAdministratorAvatar`.

**Landing on Home**
- `useAuth().login(u, p, onSuccess)` (`lib/providers/auth.tsx`) refetches `me`, writes `me.channels[0].token` to `localStorage` before invalidating queries (unless a previous channel still matches), then calls `onSuccess`. An owner has only the new store's channel, so `login(...)` then `navigate({ to: '/' })` lands on Home on the right store. This is what stock `reset-password.tsx` does.
- `api.ts` stores the `vendure-auth-token` response header in `localStorage` for any response, so an OAuth `authenticate` mutation needs only `refreshCurrentUser()` afterwards.

**Administrators and verification**
- `AdministratorService.create` → `UserService.createAdminUser`: `verified: true`, no `verificationToken`. It does **not** run `passwordValidationStrategy`.
- `AuthService.createAuthenticatedSessionForUser`: with `requireVerification` true (the default) `verified: false` returns `NotVerifiedError`, and a native credential with a `verificationToken` is refused regardless. So `User.verified` **cannot** represent "unverified but may log in" for admins: it stays `true`.
- Admin API since 3.8: `requestPasswordReset`, `resetPassword` (`admin/auth.resolver.js`). They store the **plaintext** token in `passwordResetToken`, publish `AdministratorPasswordResetEvent`, and send no email themselves.
- `UserService.updatePassword(ctx, userId, current, new)` checks the current password and validates the new one. No Admin API mutation exposes it.
- Stock `setIdentifierChangeToken`/`changeIdentifierByToken` are the customer flow and store plaintext. `AdministratorService.update({emailAddress})` changes `User.identifier` but **not** the native method's `identifier`; `UserService.changeUserAndNativeIdentifier` changes both, but not `Administrator.emailAddress`.
- **Stock `updateActiveAdministrator` (`Permission.Owner`) accepts `emailAddress` and `password`, with no current-password check.** Left alone it bypasses both change flows.
- `User.identifier` has no unique constraint; `checkForDuplicateEmailAddress` is check-then-write, so two concurrent sign-ups can both pass.

**Sessions**
- `destroyAuthenticatedSession` → `deleteSessionsByUser` removes every session. `SessionService` has no single-session delete, and `withTimeout` is private. `setSessionToken`, `extractSessionToken` are exported from `@vendure/core`.
- `@nestjs/graphql` `base-explorer.service.js` `groupMetadata`: root resolvers are `grouped[type][name] = callback`, **last one wins**. `getModules` walks the whitelisted `AdminApiModule` and then its imports, which include the plugin API modules (`api-internal-modules.js`). A plugin `@Mutation() logout` therefore replaces the stock one with no schema change. Pinned by Task 5's test.

**Banner:** `customProviders` with `location: 'layout'` wraps the authenticated `<Outlet />` only (`custom-providers.ts`, `app-layout.tsx`).

**Provisioning (P1.S1):** `ProvisionBusinessService.provision` creates Seller, Business, order sequence, the placeholder Owner role, Store + Channel (role assigned to it) and the Administrator with `customFields.businessId`, in one transaction. Role and admin creation run as SuperAdmin (A2), so an anonymous caller works. `withTransaction` joins a transaction the context already carries. The Owner role lacks `CreateAsset`, so `createAssets` is FORBIDDEN for owners.

**Repo gaps:** no asset storage is wired (`NoAssetStorageStrategy` by default); no email plugin or nodemailer in the lockfile; `i18n:check` does not exist yet (P1.S5 delivers it); `apps/storefront` has no `(platform)` routes.

## Review Focus

1. A mail scanner pre-fetches the link: the token must survive a GET. Pages POST the token only after load; `/auth/verify-email/:token` is POST. Task 7.
2. Two concurrent registrations with one email, or a double-clicked Create: one account, the other `auth.email-taken`, no orphan rows. Task 6.
3. Change password with several sessions on another instance: others die **immediately**, not after `sessionCacheTTL` (300 s), and the current one survives. Task 7.
4. An email address in mixed case or with surrounding spaces: same account in login, forgot, register and throttle keys. Tasks 1, 5 and 6.
5. A browser holding a previous account's channel, then registering: lands on the new store, not `FORBIDDEN`. Task 9.
