# P1 decisions

Decisions taken while building phase P1. Each row gives the decision, why, and the cost if it proves wrong.
Later rulings are appended under "Later rulings".

| # | Decision | Why | Cost if wrong |
|---|---|---|---|
| D1 | Snowflake ids are `String!` in GraphQL; ADR 0003 addendum. No custom `EntityIdStrategy`. | ADR 0003 §1 forbids a custom strategy; Vendure's `ID` decode does `+id`, corrupting 63-bit ids. | Renaming scalars in plugin schemas. |
| D2 | `Administrator.customFields.businessId`: `string` length 20, indexed, `internal: true`. Relation custom fields follow the integer id strategy, so a `bigint` PK does not fit (implementer confirms in Vendure source and records it in the addendum, ADR 0003 §6). | Tenant link must not be client-writable. | One custom field migration. |
| D3 | Subdomain is `varchar(30)` unique, always lowercased in domain code, with a DB `CHECK (subdomain = lower(subdomain))`, instead of `citext`. | Test databases use `synchronize: true` and have no citext extension; the check gives the same guarantee. | One column migration. |
| D4 | An archived store keeps its subdomain (unique across archived rows). | Prevents another merchant taking over a recently used host. | Later release job. |
| D5 | Platform provisioning is a SuperAdmin-only mutation `provisionBusiness`, used by the seed, tests and evidence; P1.S2 calls the same application service. | One creation path; fixtures stay GraphQL-only. | Removing one mutation. |
| D6 | A per-business placeholder Owner role (no default-channel, SuperAdmin or Customer role) is created with the first store and extended to each new store. P1.S3 replaces its permissions. | Member-of-channel is needed for any request; ADR 0002. | Replaced by design in P1.S3. |
| D7 | Channel `defaultLanguageCode` and `availableLanguageCodes` are both `[store language]`. | Dashboard content language then follows the store (P0.S2c-polish finding): `user-settings.tsx` switches when the channel does not offer the current one. | Adding languages to channels later. |
| D8 | Another business's `vendure-token` stays Vendure's `FORBIDDEN` at the auth guard; "not found" applies to ids. | The token check runs before our code and reveals nothing beyond "not yours". | Small guard change. |
| D9 | `TenantContext` is cached per `RequestContext` in a `WeakMap`; Store/Business status is read from the DB on each request (indexed lookups); Redis caching waits for a measured need. | ADR 0002 §7 needs our rows as authority, not specifically a cache now. | Add a cache behind the resolver. |
| D10 | Plugins consume tenancy only via the `@cod/plugin-tenancy` entry point. | §3a.2 forbids internals; `TenantEntity` needs typeorm, so it cannot live in `packages/shared`. | Move to a package. |
| D11 | `changeStoreSubdomain` mutation exists now (API only); UI and DNS stay in P8.S9. | Acceptance needs a real subdomain change to prove invalidation. | Removing one mutation. |
| D12 | Storefront calls `GET /store/resolve` on each proxy pass, without its own cache; server-side LRU + Valkey handles load. P3.S2 may add a proxy tier. | Keeps invalidation in one place. | Adding a tier. |
| D13 | `Order.customFields.orderNumber/businessId/storeId` are declared by P3.S4, which assigns them. This session ships the sequence service only. | Nothing writes them before P3.S4. | One migration. |
| D14 | Platform defaults keep converging on every migrate (no create-if-missing). | Currency, tax and languages are platform invariants, and the store flow depends on them. | Small seed edit. |
| D15 | "Default agent" in the acceptance list is the delivery agent, i.e. `defaultCarrierId`. | Same concept in the research captures. | Renaming a column. |

## Later rulings

| # | Decision | Why | Cost if wrong |
|---|---|---|---|
| D16 | Host keys in Valkey carry a 24 h TTL (`HOST_CACHE_TTL_SECONDS`), a deviation from ADR 0006's "no TTL". Invalidation stays the normal path; failed deletes are retried for about 30 s (`HOST_INVALIDATE_RETRIES`). | If Valkey is down for every delete, a key with no TTL would serve an old host for ever once Valkey returns. | One database read per host per day; if 24 h is too long, a moved host can stay stale that long after an outage outlasting the retries. |
| D17 | The storefront's `use cache` store name is not revalidated on rename in P1.S1; revalidation arrives with the publish flow (ADR 0006 §5, P3.S2). | The `storefront-revalidate` path belongs to that flow; host data itself is invalidated now. | A store's page shows its old name for up to the cache life. |
| D18 | The stock store switcher keeps showing the random channel code and archived stores until P1.S5. | Plan Task 4 mandates a random code, and P1.S5 owns the switcher. | Until P1.S5 an owner with several stores sees opaque names. |
| D19 | `classifySubdomain` rejects `xn--` labels; `PLATFORM_DOMAIN` must be a lowercase DNS name at boot. | Punycode can imitate another store; a malformed domain makes every store 404 with no error. | Merchants cannot register IDN labels, which the format never allowed in readable form. |
| D20 | Public auth pages are dashboard routes: extension `/register`, `/verify-email`, `/confirm-email-change` (`authenticated: false`) plus stock `/forgot-password`, `/reset-password`. Reverses a user-accepted part of ADR 0010 and ADR 0006 item 11 (Next.js `/(platform)/*`). Addendum on both, marked "Accepted (2026-11-09, standing user authorization for P1)"; the handoff lists it as a reversal for the user to see. | The brief's acceptance needs landing on Home after submit. ADR 0010 forbids a token handoff across origins; same-origin `login` gives it. Stock reset pages already exist there. Spike A proved the route. | Move three pages to Next.js and accept a login step after sign-up. |
| D21 | Plugin resolvers shadow exactly four stock mutations: `logout`, `requestPasswordReset`, `resetPassword`, `updateActiveAdministrator`. Same schema. | Stock dashboard pages call them by name and cannot be replaced; each has a defect for us. Smaller than a `pnpm patch`. | M.S1 re-runs the pinning tests; a loss means one patch. |
| D22 | `logout` ends the **current** session only: delete the row by `ctx.session.token`, then `sessionCacheStrategy.delete`, then clear the cookie with `setSessionToken`, and publish `LogoutEvent`. | ADR 0017 §3: smallest fix; native sessions must survive it. | Restore stock behaviour by deleting one resolver. |
| D23 | Email verification is `Administrator.customFields.emailVerifiedAt` (datetime, nullable, `internal: true`). `User.verified` stays `true`. Migration backfills existing administrators to `createdAt`. | `verified: false` blocks login, and the brief wants unverified login. Internal fields cannot be written through stock inputs. | One field migration. |
| D24 | `account_token` is an **account-level** table, not a `TenantEntity`. It is reached before any tenant context exists (anonymous links), keyed by Vendure `User` id, which is global like `user` and `session`. Lookups are only by HMAC or by `ctx.activeUserId`. | No business can be derived for an anonymous token; a business id would be a denormalised copy and give no isolation. | Add a `businessId` column. |
| D25 | Tokens are 32 random bytes base64url, stored as HMAC-SHA-256 with `AUTH_TOKEN_SECRET`; OTP is 6 digits under the same HMAC (a bare hash of 10^6 values is reversible). Consumed by a conditional `UPDATE … WHERE "consumedAt" IS NULL`. A new token of a purpose voids the previous ones. | Single-use and stored hashed. | Rotation of a secret voids open tokens only. |
| D26 | Values: verify link 24 h; OTP 10 min, 5 wrong tries then locked until a resend; resend cooldown 60 s; reset 1 h; email change 24 h. Constants in `packages/shared/src/auth/constants.ts`. | Brief; defaults otherwise. | Constant change. |
| D27 | A taken email at registration **is** disclosed (`auth.email-taken`). Every other flow (login, forgot, resend, change-email target) is enumeration-safe. | Registration signs the user in immediately, so a silent success cannot be honest. Mitigated by the registration limit and the challenge. | Move to a confirm-first sign-up: changes the wizard ending. |
| D28 | `plugins/rate-limit`: `RateLimiter` (Valkey Lua token bucket) and `@RateLimit(policy)` guard, imported by auth and tenancy. | Tenancy's public availability routes need it, and tenancy cannot import auth (auth imports tenancy). | Fold into another plugin. |
| D29 | Policies (capacity per window): `login-pair` 10/min failures per (normalised email, IP), then lockout of that pair, 60 s doubling to 1 h, cleared on success or reset. `login-account` 10/min failures per email, a flat limit with no lockout that **never blocks a correct password**. Both apply whether or not the email exists. `login-ip` 60/min. `reset-account`, `otp-account`, `current-password-account` (change password, request email change) 10/min; `reset-ip`, `otp-ip`, `current-password-ip` 60/min. `register-ip` 20/h. `subdomain-ip` 60/min. | ADR 0008, ADR 0017 §5 (IP 60/min for CGNAT). A lockout keyed by email alone lets anyone hold a victim out indefinitely. | Constants. A distributed guesser is bounded only by the IP limit. |
| D30 | Over limit: REST `429` + `Retry-After`. GraphQL: error code `RATE_LIMITED`, `extensions.retryAfterSeconds` and the `Retry-After` header on a 200, because Apollo owns the status. The login strategy **throws** it so the stock form shows the message. | ADR 0017 §5 wording is REST-shaped; the dashboard shows `error.message` from a throw. | Small mapping change. |
| D31 | Valkey outage: `login-*`, `reset-*`, `otp-*` and `current-password-*` fall back to an in-process bucket per api process, with the same policies; other policies fail open. Both log an error. The limiter's client uses `enableOfflineQueue: false` and a command timeout of 250 ms. Client IP comes from `ClientIpResolver`: `CLIENT_IP_HEADER` empty means `req.ip`; set (production: `cf-connecting-ip`) it reads that header when it holds a valid IP, else `req.ip`. | `redis-cache-strategy.js:45` swallows errors, so login stays up during an outage and would be unthrottled. ioredis queues commands offline, which would hang requests. Behind the edge `req.ip` (`TRUSTED_PROXY_HOPS = 1`) is a Cloudflare address (`system-design.md:371`). | Limits are per process during an outage. A set header is spoofable if the origin is reachable around the edge. |
| D32 | Email: `EmailSenderPort` + `nodemailer` adapter, sent by the worker from JobQueue `auth-email`. The job payload is sealed AES-256-GCM with a key derived from `AUTH_TOKEN_SECRET`. Templates are TS render functions with escaped values in `apps/server/src/email/`, injected through `AuthPlugin.init`. | System design: outbound calls run in workers. Raw tokens must not sit readable in Valkey. A plugin cannot import `apps`. | Swap adapter or template engine behind the port. |
| D33 | Asset storage: `AssetServerPlugin` + `configureS3AssetStorage` on the existing Garage bucket `S3_BUCKET_PRIVATE`, prefix `assets/`, served by the api at `/assets`. P2 replaces bucket and naming. | Photo and logo need storage now; no new bucket or compose service. | P2 repoints config and moves few files. |
| D34 | Logo: after `login`, the wizard calls `uploadBusinessLogo(file)` (`TenantBusiness` update, ≤5 MB, image types only), which creates the asset on the active channel via `AssetService`, then the wizard calls `updateBusiness` and `updateStore` with the id. A failed upload never fails registration. | `provisionBusiness` refuses a logo and the Owner role lacks `CreateAsset`. `/store/resolve` reads the store's logo. | Remove one call. |
| D35 | Sign-up challenge: `BotChallengePort`, `Turnstile` and `Noop` adapters, `TURNSTILE_ENABLED` default `false`. Outage fails open. The widget is an iframe from `TURNSTILE_CHALLENGE_URL`; that page is P3.S4's. | ADR 0008 and ADR 0017 §3 require Turnstile on sign-up, while ADR 0012 says "on the COD submit only" and ADR 0008 bans third-party scripts in the dashboard. Hence a mockable server check, off until the iframe page exists. **Flagged in the handoff.** | Sign-up is unchallenged until enabled. |
| D36 | OAuth is a redirect code flow with PKCE (`/auth/oauth/:provider/start` and `/callback`), never a provider script in the dashboard. The callback issues a 5-minute single-use ticket in `account_token`, consumed by strategy `oauth` through `authenticate`. `state` and the ticket are bound to an HttpOnly cookie set at `/start` (login CSRF). The subject persists as Vendure's `ExternalAuthenticationMethod`. Departs from ADR 0008's "verifying ID tokens"; addendum in Task 1. Auto-link only when the provider confirms the email and the existing account's email is verified; otherwise `auth.oauth-link-requires-verification`. A new identity goes to `/register?ticket=` and finishes steps 2-3. Strategies are registered only when `AUTH_OAUTH_ENABLED`. | ADR 0008 no third-party scripts. Linking to an unverified account would keep an attacker's pre-set password. A user with no business cannot use the dashboard. | Rework around ID tokens. |
| D37 | Password policy: 8 to 72 UTF-8 bytes (bcrypt's limit). Shared schema, `AccountPasswordValidationStrategy` for Vendure paths, and an explicit check before `provision`, which does not validate. | Stock minimum is 4; `createAdminUser` skips validation. | Constants. |
| D38 | Account pages at `/account/profile` and `/account/security`, in a nav section `account`. Stock `/profile` stays reachable; its server path is restricted by D21 (same email passes, a different email or any password is refused with `auth.use-account-security`). P1.S5 repoints the user menu. | The stock path cannot be replaced safely. | One redirect later. |
| D39 | `SubdomainAvailability` gains `reasonCode` (`length`, `format`, `punycode`, `reserved`, `taken`, or null); `reason` stays English for API users. The wizard maps codes to catalogue ids in AR, FR, EN. | Handoff P1.S1: reasons are English until the wizard maps them. | Additive field. |
| D40 | Until P1.S5 delivers `i18n:check`, a `plugins/auth` unit test enforces catalogue parity: every id used in `dashboard/` exists non-empty in `en.po` and `ar.po`, and `subdomain.*` also in `fr.po`. | The check the brief names does not exist on this branch. | Delete the test once `i18n:check` covers it. |
| D41 | Registration and email-change confirm take `pg_advisory_xact_lock(hashtextextended('account-email:' || $1, 0))` on the normalised email. | No DB uniqueness on identifiers, and a partial index on a core table fails the migration-drift test. Transaction-scoped, so PgBouncer-safe (ADR 0016 §6). | Add a claim table. |
| D42 | Queue `auth-email` is a named constant now and joins P1.S6's registry (`packages/shared/src/queues.ts`, ADR 0013 taxonomy, critical pool). `WORKER_ACTIVE_QUEUES` stays empty (ADR 0013 addendum: nothing sets `activeQueues` before P1.S6), so every worker consumes it. | The registry is P1.S6's, parallel to this session: add the entry if merged first, otherwise the later of the two adds it. | A pool that omits the queue leaves mail unsent. |
| D43 | `account_token` rows are purged by a scheduled task `account-token-purge` (daily) 7 days after expiry or consumption. | They hold `pendingEmail`, which is personal data. | Task removal. |
| D44 | Policy `otp-account-daily`: 50 verification code guesses per user per day (token bucket, in-process during an outage), on top of `otp-account` 10/min and the 5-try lock of each code. | A resend issues a code with fresh tries, so the lock alone gives an unbounded number of guesses over time. 50 allows ten fully wasted codes a day and keeps a guesser at 5 in 100 000 per day. | A user who burns the cap waits for the bucket to refill, about 29 minutes per guess; the link in the mail still works. |
