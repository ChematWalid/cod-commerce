# ADR-0003: Identifiers (Vendure default ids for core, snowflake ids for our entities)

**Date**: 2026-11-07
**Status**: Proposed
**Deciders**: architect, user

Citation keys: [VN §n] = `docs/architecture/research/vendure-v3.md` section n; [DM] = `docs/research/data-model.md`; [BK] = background knowledge, verify before relying on it.

## Context

- The reference product uses 18-digit snowflake-style ids, sent as **strings** in JSON, on every row [DM intro, "Product"]. Ids are part of the functional shape the storefront and public API expose (`productId`, `variantId`, order ids).
- Vendure core entities use the configured `EntityIdStrategy`; the default is auto-increment integers, exposed through the GraphQL `ID` scalar (a string on the wire). The id strategy must be chosen before the first migration and can practically never change afterwards [BK].
- Our own tables (orders read model, outbox, activity log, ledgers, …) need **time-ordered** ids: ADR 0016 uses keyset pagination on `(created_at desc, id desc)` and range partitioning; `docs/architecture/README.md` asks 0003 to keep snowflake-style `bigint` ids.
- JavaScript numbers are exact only up to 2^53 − 1 (16 digits). An 18-digit id parsed as a JS `number` is silently corrupted.
- Sequential ids in public URLs or payloads leak volumes (orders per business, platform-wide order count) and are enumerable.

## Options

1. **Vendure default ids everywhere** (integers in core and in our entities): simplest, one type. But our high-volume tables lose time ordering by id across partitions, ids generated per table need a DB round-trip (no id before insert, which the outbox/idempotency flows want), and every public id is sequential and enumerable.
2. **Snowflake strings everywhere, including core via a custom `EntityIdStrategy`**: one id shape across the platform. But Vendure's `EntityIdStrategy` offers `primaryKeyType: 'increment' | 'uuid'` [BK, verify], so a snowflake core PK needs a DB-side default function or a core patch (ADR 0001 escape hatch), departs from the tested Vendure path for every core table and migration, and is irreversible.
3. **Hybrid (recommended)**: Vendure core keeps its default ids; our custom entities use snowflake `bigint` ids; public APIs follow one mapping rule.

## Decision

Option 3.

1. **Core entities** (Product, ProductVariant, Order, Customer, Channel, Administrator, Asset, …) keep Vendure's default `AutoIncrementIdStrategy` (integer). We never configure a custom `EntityIdStrategy`.
2. **Our entities** (everything extending `TenantEntity`, ADR 0002, plus platform tables) use a **snowflake id** stored as Postgres **`bigint`**, generated in the application before insert (`@PrimaryColumn({ type: 'bigint' })`, never `@PrimaryGeneratedColumn`). Foreign keys to our entities are `bigint`; foreign keys to core entities keep the core integer type (`Store.channelId`, `Store.sellerId`, `cod_order.vendure_order_id`).
3. **Generator spec** (`packages/shared/ids`, one implementation used by api, worker and scripts):
   - 64-bit layout, sign bit always 0: **41 bits** milliseconds since the custom epoch | **10 bits** worker id (0–1023) | **12 bits** sequence (4,096 ids per ms per worker).
   - **Epoch `2025-01-01T00:00:00Z`**. Ids generated today have **18 decimal digits** (from 2025-10 until about 2032-07, then 19 digits; the 41-bit range lasts until about 2094). Digit count is not a contract: clients must treat ids as opaque strings.
   - **Worker id**: leased at process start from Valkey (`SET idgen:worker:{n} <instance> NX PX 60000`, renewed every 20 s, first free `n`); a process that loses its lease stops generating ids and re-leases. Scripts and tests use a reserved range (1000–1023).
   - **Clock**: if the clock moves backwards by ≤ 5 ms the generator waits; by more, it throws and the process re-leases a worker id. Sequence overflow within a millisecond waits for the next millisecond.
   - The time part is the creation time, so `ORDER BY id` ≈ creation order and `id` ranges can bound partitions (ADR 0016).
4. **Serialization rule**: ids are **always strings** outside the database — in TypeScript (`type Snowflake = string & { __brand: 'Snowflake' }`, never `number` or `bigint` in DTOs), in GraphQL (`ID!` scalar), in REST/JSON, in job payloads, webhooks, logs and URLs. TypeORM returns `bigint` columns as strings by default; we never set `bigNumberStrings: false` or parse ids with `Number()`/`parseInt`. Shared zod schema `Id = z.string().regex(/^[1-9][0-9]{0,18}$/)`.
5. **Mapping rule for public APIs** (storefront `/store/*`, public REST v1, outbound webhooks, MCP, embedded-app tokens):
   - Our entities are exposed by their snowflake id (string).
   - **Order, Customer, Administrator, Payment, Fulfillment and Seller** core ids are **never** exposed publicly. Each maps to our own entity id: order → `cod_order.id` (plus the human order number), customer → `customer_profile.id`, administrator → `business_member.id`.
   - Catalog core ids (Product, ProductVariant, Collection, Asset) are exposed as **opaque decimal strings** (the integer as text). The catalog is public anyway, so enumeration leaks little; clients must not assume they are sequential or distinguishable from snowflakes.
   - Internal GraphQL (Admin API, dashboard) uses Vendure's ids as Vendure does.
6. **Custom fields on core entities** that hold our ids (e.g. `Order.customFields.businessId/storeId`): prefer a **relation** custom field to the `Business`/`Store` entity (column type follows our `bigint` PK); if Vendure's relation custom fields do not accept a `bigint` PK, use a `string` custom field (length 20, indexed). P1.S1 verifies and records which.

## Consequences

### Positive
- Core stays on the tested Vendure path; no patch, no irreversible core id decision.
- Our high-volume tables get time-ordered, partition-friendly ids generated without a DB round-trip (outbox and idempotency keys can be assigned before insert).
- Public payloads keep the reference's id shape (18-digit strings) and never leak order or customer counts.

### Negative
- Two id types in the codebase (core integer, our `bigint` string); joins between them need explicit types.
- A worker-id lease in Valkey is a new moving part.

### Risks
- **An id handled as a JS number** loses precision silently. Mitigation: branded `Snowflake` type, zod schema at every boundary, a JSON round-trip test with an id above 2^53, and lint bans `Number(`/`parseInt(` on `*Id` identifiers.
- **Duplicate worker ids** (lease bug, Valkey failover) could produce duplicate ids. Mitigation: unique PKs make a duplicate a failed insert, not corruption; the generator logs its worker id; a failover forces re-lease.
- **Clock jumps** on a host. Mitigation: NTP on all nodes, the backward-clock rule above, alert on generator errors.
