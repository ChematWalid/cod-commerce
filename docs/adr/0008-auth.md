# ADR-0008: Authentication and authorization surfaces

**Date**: 2026-11-07
**Status**: Accepted (2026-11-07), approved by the user after P0.S2a-1/P0.S2a-2 review
**Deciders**: architect (draft), user

Citation keys: [VN §n] = `docs/architecture/research/vendure-v3.md` section n; [API "…"] = `docs/research/api-surface.md` bullet; [BK] = background knowledge, verify before relying on it.

## Context

- The reference dashboard uses a custom JWT in localStorage plus `__Host-` cookies [API "Auth"]. P0.S2a says to prefer Vendure's built-in session tokens unless there is a concrete need.
- With several instances, Vendure needs shared sessions. From v3.1 `DefaultSessionCacheStrategy` uses the configured `CacheStrategy` (RedisCachePlugin), and with cookie sessions all instances share `cookieOptions.secret` [VN §1, §3].
- **Vendure 3.8 token facts** (context7 `/vendurehq/vendure/v3.8.0`): `authOptions.tokenMethod` accepts `'cookie' | 'bearer'` or an array of them (and `'api-key'` since 3.6); the default is `'cookie'`. The React dashboard uses **bearer** when the server's `tokenMethod` includes `'bearer'`: it reads the session token from the response header named by `authOptions.authTokenHeaderKey` (default `vendure-auth-token`) and stores it in `localStorage`, then sends `Authorization: Bearer <token>`.
- Surfaces: dashboard users (merchants, members with 94 permissions, platform staff), public storefront (no login), public Admin API keys (P9.S8a), MCP clients over OAuth (P9.S8b), inbound webhooks (carriers, payments, Shopify, WhatsApp), outbound signed webhooks, internal service calls.

## Options

1. **Custom JWT (reference shape)**: stateless, but revocation needs a deny-list anyway, it duplicates Vendure's auth and roles, and the tokens would sit in localStorage. Rejected.
2. **Vendure built-in sessions for humans + purpose-built credentials for machines (recommended).**

**Public storefront endpoints** (the reference's `/store/*` quote/catalog routes and `/business/:bid/orders/public`, `/business/:bid/orders/abandoned-checkouts/public` [API "Storefront (public…)"]):
- **No user authentication.** Our equivalents are same-origin storefront route handlers (`/api/store/quote`, `/api/store/shipping-quote`, `/api/store/orders`, `/api/store/abandoned-checkouts`, catalog reads) that proxy to the internal API with the signed internal header (ADR 0006); the API's `/store/*` routes are not public.
- **Store resolution**: the store and business come **from the host** (resolved in `proxy.ts`). A `storeId` or `businessId` in the path or body is never used to select the tenant; if present and different from the host's, the request is rejected (400, logged as a spoofing signal). We do not copy the reference's `/business/:bid/...` public path shape.
- **CORS**: none. Browser calls are same-origin, the route handlers send no `Access-Control-Allow-Origin`, so another site cannot call them from a browser. The builder preview is on the store host too.
- **Rate limiting per IP + device**: Cloudflare edge rules per IP first; then Redis token buckets per (store, device id) and a high per (store, IP) limit (CGNAT) for quotes (429 with `Retry-After`) and for intake (over the limit the order is **held for review**, never rejected; see below). `deviceId` is a localStorage uuid, an abuse signal only; Turnstile on submit.
- **Quote token as the price commitment** (ADR 0004): intake accepts an order only with a valid `quoteToken` whose signature, expiry, store/business (against the host) and cart hash match; prices are taken from the token, and a token creates at most one order.

**Rate limits** (Redis token buckets, plus Cloudflare at the edge):
- Login, reset and OTP: per IP + per account (10/min, lockout with backoff).
- Admin API: per business, 20 rps sustained, burst 100.
- Public API: per key, 10 rps default, plan-dependent.
- Storefront intake: per (store, device) first, a high per (store, IP) limit (Algerian mobile CGNAT shares IPs), plus a global per-store cap; exceeding any of them holds the order for review, never a 429.
- MCP: dynamic client registration rate-limited per IP and garbage-collected after 30 days unused; per-grant tool-call rate limit.
- Sign-up and trial: Turnstile on sign-up; AI credits and WhatsApp sending unlocked only after email verification (abuse of free credits).
- Details in system-design §4 and §7.

**Cookies and headers**: the dashboard is same-origin with the Admin API (no CORS). `apiOptions.cors` is restricted to `app.ourdomain` and exposes the `authTokenHeaderKey` header (needed if the dashboard is ever served from another origin). The session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, with `cookieOptions.secret` shared by all instances. `trustProxy` is set for Cloudflare/LB [VN §1]. HSTS, CSP (nonce-based on storefront; pixels allow-listed), `X-Frame-Options` except the builder preview (frame-ancestors `app.ourdomain`).

## Consequences

### Positive
- Reuses Vendure auth, roles and sessions. Revocation is a session delete.
- Every machine credential is scoped to one business, can be revoked, and is stored hashed.

### Negative
- A custom 2FA strategy and an OAuth server for MCP are ours to build (P10.S2, P9.S8b).

### Risks
- **Bearer tokens in browser storage are exposed to XSS.** Mitigation: strict CSP on the dashboard, no third-party scripts in the dashboard, short-lived sessions for staff. If spike A shows the dashboard works on cookies alone, switching to `tokenMethod: 'cookie'` is a one-line change and removes the token from `localStorage`.

## Evidence

- [x] dashboard sends Authorization: Bearer (spike A, 2026-11-07, Vendure 3.8.1 on Node 24.22.1, SQLite because Docker was unavailable; details in ADR 0010 Evidence). With `authOptions.tokenMethod: ['cookie', 'bearer']` the React dashboard stored the session token in `localStorage['vendure-session-token']` and sent `Authorization: Bearer <token>` on every Admin API request after login; the HttpOnly `session`/`session.sig` cookies were sent too. Control run with `tokenMethod: 'cookie'`: login and the product list worked with no `Authorization` header and no token in `localStorage`, so the cookie-only switch named under Risks is confirmed to work. (The 3.8.1 scaffold defaults to `['bearer', 'cookie']`.)

## Addendum (2026-11-09): P1.S2 decisions D21, D35, D36

**Status**: Accepted (2026-11-09, standing user authorization for P1)

1. **D21: four stock Admin API mutations are shadowed by plugin resolvers**: `logout`, `requestPasswordReset`, `resetPassword` and `updateActiveAdministrator`, with the same schema. The stock dashboard pages call them by name and cannot be replaced; each has a defect for us (logout ends every session, the reset pair sends no email and stores plaintext tokens, and `updateActiveAdministrator` changes email and password with no current-password check). This is the smaller alternative to a `pnpm patch` (ADR 0001 section 5). M.S1 re-runs the pinning tests.
2. **D35: the sign-up challenge is a server-side port.** ADR 0008 asks for Turnstile on sign-up and also bans third-party scripts in the dashboard, and ADR 0012 limits Turnstile to the COD submit. So `BotChallengePort` has a Turnstile and a no-op adapter, controlled by `TURNSTILE_ENABLED` (default `false`), and fails open on a provider outage. The widget is an iframe from `TURNSTILE_CHALLENGE_URL`; that page belongs to P3.S4. Until it is enabled, sign-up has no challenge.
3. **D36: OAuth uses a redirect code flow with PKCE instead of verifying ID tokens.** This replaces "Google/Facebook via custom `AuthenticationStrategy` verifying ID tokens" in the table: the api serves `/auth/oauth/:provider/start` and `/callback`, so no provider script runs in the dashboard. The callback issues a 5-minute single-use ticket, which strategy `oauth` consumes through `authenticate`. `state` and the ticket are bound to an HttpOnly cookie set at `/start` against login CSRF. The subject is stored as Vendure's `ExternalAuthenticationMethod`. An existing account is linked only when the provider confirms the email and the account's email is verified; otherwise the error is `auth.oauth-link-requires-verification`. Strategies exist only when `AUTH_OAUTH_ENABLED`.
