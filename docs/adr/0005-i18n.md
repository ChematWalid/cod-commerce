# ADR-0005: Internationalisation (dashboard ar/en, storefront ar/fr/en, RTL, DZD formatting)

**Date**: 2026-11-07
**Status**: Proposed
**Deciders**: architect, user

Citation keys: [VN §n] = `docs/architecture/research/vendure-v3.md` section n; [BK] = background knowledge, verify before relying on it.

## Context

- Merchants work in Arabic or English; inventory rows "Arabic dashboard (RTL, IBM Plex Sans Arabic)" and "Locale switch EN/AR with RTL layout" are built in P1.S5. Buyers see storefronts in the store's language: Arabic (RTL), French or English (README assumptions, ADR 0006).
- The Vendure React dashboard has **built-in RTL**: `useDisplayLocale().isRTL` sets `html[dir]` and a Radix `DirectionProvider`, and it ships an `ar.po` catalogue. Extension strings use **Lingui** `.po` catalogues per plugin (`lingui.config.js`, `npx lingui extract`) [VN §7]. Whether every built-in screen is RTL-correct is answered by spike A (c) in ADR 0010.
- The dashboard extension code path is fixed by ADR 0010: `plugins/<name>/dashboard/` (Option 1), mapped to `apps/admin/src/features/<name>/` if 0010 picks Option 2.
- The storefront caches buyer-agnostic HTML per (host, path) (ADR 0006): a page render may not read `Accept-Language` or cookies, so the locale must come from the store and the route.
- Money is integer DZD; the stored precision (exponent 0 vs Vendure's default minor units ×100) is decided in ADR 0004 from spike B.
- Copy is written fresh with neutral keys; no reference-product wording (ADR 0007).

## Options

1. **One i18n library for everything** (e.g. ICU JSON + one runtime in dashboard and storefront): one format, but fights the Vendure dashboard, which is built on Lingui and ships its own `.po` catalogues.
2. **Follow each host's native stack (recommended)**: Lingui `.po` in the dashboard (as Vendure does), ICU JSON catalogues with a light runtime in the Next.js storefront, shared domain labels in `packages/shared`.
3. **Per-app duplicated catalogues without a shared package**: simplest start, but status names, wilaya labels and error codes drift between dashboard, storefront and notifications.

## Decision

Option 2.

**Dashboard (ar/en)**
- Display languages `en` (source) and `ar`; French for the dashboard is out of scope until a roadmap session adds it.
- Extension strings via Lingui macros; catalogues at **`plugins/<name>/dashboard/i18n/{en,ar}.po`** (ADR 0010's path; if 0010 chooses Option 2 this becomes `apps/admin/src/features/<name>/i18n/{en,ar}.po` with the same rules).
- RTL comes from the dashboard's own `isRTL` → `html[dir="rtl"]`. Our extension components use only logical CSS (`margin-inline-start`, Tailwind `ms-/me-/ps-/pe-/start-/end-`); a lint rule bans physical `ml-/mr-/pl-/pr-/left-/right-` utilities in `plugins/*/dashboard` and the storefront. Directional icons mirror under `[dir="rtl"]`.
- Font: **IBM Plex Sans Arabic** (OFL) for Arabic with **IBM Plex Sans** for Latin, self-hosted woff2 (Arabic + Latin subsets, `font-display: swap`) loaded by the extension CSS (spike A (c) verifies).

**Storefront (ar/fr/en)**
- **Locale routing per store**: each `Store` has a default `language` (ADR 0002) and an optional list of extra enabled locales. `proxy.ts` resolves the host, then the locale: the store default for unprefixed paths, or the path prefix `/fr`, `/en`, `/ar` when that locale is enabled for the store (otherwise 404). It rewrites to `/_t/[storeId]/[locale]/...`, so the locale is a route param inside every cache key (ADR 0006). There is **no server-side `Accept-Language` negotiation** (it would break buyer-agnostic caching); a language switcher links to the prefixed paths, and `hreflang` alternates are emitted for enabled locales.
- The root layout of `/_t/[storeId]/[locale]` sets `<html lang={locale} dir={locale === 'ar' ? 'rtl' : 'ltr'}>`.
- Runtime: ICU MessageFormat via a light runtime (`next-intl` or equivalent, chosen in P0.S2b), messages loaded per locale and namespace in server components; client components get only the namespaces they need.
- Same fonts as the dashboard via `next/font/local` (self-hosted, no third-party font request).

**Translation file layout**
```
packages/shared/i18n/{ar,fr,en}/<namespace>.json   ICU messages shared by storefront, API notifications (SMS/WhatsApp/email) and server errors
                                                   namespaces: common, product, checkout, order-status, errors, notifications
apps/storefront/i18n/{ar,fr,en}/<namespace>.json   storefront-only UI strings (sections, builder presets)
plugins/<name>/dashboard/i18n/{en,ar}.po           dashboard extension strings (Lingui)
```
- Domain labels used by both dashboard and storefront (order statuses, delivery types, error codes) are **defined once** in `packages/shared/i18n`; a build script generates the matching Lingui entries for the dashboard, so the two never drift.
- Wilaya and commune names are **data** (Arabic and Latin name columns, imported in P2), not catalogue strings.
- Merchant content (product names, descriptions, pages) is entered once in the store's language and stored in Vendure translations with `languageCode` = store language. Multi-language merchant content is out of scope until a roadmap session adds it.
- **Checks in CI**: every key exists in every locale of its catalogue (missing key fails); Arabic messages with counts use ICU plural categories `zero, one, two, few, many, other`; no hard-coded user-facing strings in components (lint).

**Neutral copy keys** (ADR 0007): keys name the function, not the wording (`checkout.submit`, `orderStatus.confirmed`, `errors.quoteExpired`); all text is written fresh, never copied from the reference product.

**Numbers, money, dates**
- One formatter module in `packages/shared` (`formatMoney`, `formatNumber`, `formatDate`) used by dashboard, storefront and notifications.
- **DZD**: `Intl.NumberFormat` with `ar-DZ` / `fr-DZ` / `en` and `maximumFractionDigits: 0`; **Latin digits in every locale** (`numberingSystem: 'latn'`, which matches Algerian usage and phone numbers); symbol `د.ج` in Arabic and `DA` in French/English. The formatter takes the stored integer and the precision chosen in **ADR 0004** (it divides by 100 only if 0004 keeps Vendure's minor units); no floating-point arithmetic, display only.
- Dates: Gregorian calendar, displayed in `Africa/Algiers`, stored in UTC.
- Phone numbers, order numbers and other LTR tokens inside RTL text are wrapped in `<bdi>` / `dir="ltr"`.

## Consequences

### Positive
- Uses the dashboard's native Lingui and RTL support instead of fighting it; the storefront stays cache-friendly because the locale is part of the route.
- Shared domain labels and one money formatter keep dashboard, storefront and notifications consistent.

### Negative
- Two message formats (Lingui `.po` and ICU JSON) plus a generation step between them.
- Built-in Vendure dashboard screens depend on Vendure's own `ar.po` quality; gaps need upstream contributions or CSS/locale overrides.

### Risks
- **RTL gaps in built-in dashboard screens.** Mitigation: spike A (c) lists broken elements; CSS overrides in our extension; ADR 0010's fallback rule if they cannot be fixed.
- **Money display off by ×100** if the formatter and ADR 0004 disagree. Mitigation: the formatter reads the precision from one shared constant set by 0004, with a unit test on 9 100 DZD.
- **Physical CSS slipping into components.** Mitigation: lint rule above, RTL screenshots in UI PRs (CLAUDE.md browser check).
