# ADR-0008: Authentication and authorization surfaces

**Date**: 2026-11-07
**Status**: Proposed (draft for P0.S2a)
**Deciders**: architect (draft), user

## Context

- The reference dashboard uses a custom JWT in localStorage plus `__Host-` cookies [API "Auth"]. P0.S2a says to prefer Vendure's built-in session tokens unless there is a concrete need.
- With several instances, Vendure needs shared sessions. From v3.1 `DefaultSessionCacheStrategy` uses the configured `CacheStrategy` (RedisCachePlugin), and with cookie sessions all instances share `cookieOptions.secret` [VN §1, §3].
- Surfaces: dashboard users (merchants, members with 93 permissions, platform staff), public storefront (no login), public Admin API keys (P9.S8a), MCP clients over OAuth (P9.S8b), inbound webhooks (carriers, payments, Shopify, WhatsApp), outbound signed webhooks, internal service calls.

## Options

1. **Custom JWT (reference shape)**: stateless, but revocation needs a deny-list anyway, it duplicates Vendure's auth and roles, and the tokens would sit in localStorage. Rejected.
2. **Vendure built-in sessions for humans + purpose-built credentials for machines (recommended).**

## Decision

| Actor / surface | Authentication | Authorization | Tenant binding |
|---|---|---|---|
| Merchant, member (dashboard at `app.ourdomain`, Admin API same-origin `/admin-api`) | Vendure session token (bearer, as the React dashboard uses; spike A confirms). Email+password `NativeAuthenticationStrategy`; Google/Facebook via custom `AuthenticationStrategy` verifying ID tokens (P1.S2). Sessions cached in Redis. `sessionDuration` 30 d sliding, revoked on password change or member removal. | Vendure channel-scoped Roles + our permission catalog (93 permissions, P1.S3) + `requireFeature()` plan gates (P9.S1). | `businessId` from `Administrator.customFields.businessId`. The active store channel must belong to it (ADR 0002). |
| Platform staff | Same, plus **mandatory TOTP 2FA** (custom strategy, P10.S2), with an IP allow-list option. | Superadmin / staff roles on the default channel. | Cross-tenant by design. Every impersonation needs a reason and is written to the audit log. |
| Buyer on storefront (public) | None. A device id (uuid in localStorage) is an anti-abuse signal, not identity. **Turnstile** token on order submit (ADR 0012). | Only public, read-only catalog and quote endpoints plus intake. The quote token is the price commitment (ADR 0004). | Store from host via the storefront proxy (ADR 0006). A body `storeId` must equal the host store or the request is rejected. |
| Public Admin API (REST v1, P9.S8a) | API key `pk_live_<keyId>_<secret>`. Only the SHA-256(secret + pepper) is stored. Shown once. Optional IP allow-list and expiry. | Scopes (`orders:read`, `orders:write`, `products:read`, …) intersected with the creating member's permissions at call time. | The key belongs to exactly one business, with an optional store restriction. |
| MCP clients (Claude, ChatGPT; P9.S8b) | OAuth 2.1 authorization-code + PKCE, dynamic client registration and protected-resource metadata, as the MCP authorization spec requires [BK, verify the current spec revision in P9.S8b]. The consent screen is in the dashboard (`/mcp/oauth/approve`). Access token 1 h, rotating refresh token 30 d, revocable from Apps. | Scopes = API-key scopes. Tools also enforce the approving user's role permissions. MCP never spends AI credits (README shared contracts). | One business per grant. |
| Inbound webhooks (`api.ourdomain/webhooks/{provider}/{accountKey}`) | Provider signature where offered (Chargily HMAC, Stripe signature, Shopify HMAC, WhatsApp `X-Hub-Signature-256`, Yalidine webhook secret [feature-inventory X "Carrier connect forms"]). Otherwise an unguessable per-account `accountKey` (128-bit) in the path plus an IP allow-list if the carrier publishes one. | Gateway only (ADR 0016). No user context. | `accountKey` → carrier account → business. |
| Outbound webhooks (P9.S8a) | `X-Signature: t=<unix>,v1=<HMAC-SHA256(secret, t + "." + body)>`, 5 min tolerance, per-subscription secret, rotation with dual secrets for 24 h. | n/a | Per business subscription. |
| Internal service-to-service (storefront → API, revalidate) | HMAC header `x-internal-sig` = HMAC-SHA256(secret, method, path + query, timestamp, `x-store-id`, `x-client-ip`, `x-client-country`, SHA-256(body)), 60 s skew, versioned secret (`kid`). Binding the headers and body means a captured or forged request cannot be re-targeted at another store. Private network, the edge blocks the routes, and `InternalOnlyGuard` enforces it in the api role on every host (the Cloudflare-IP allow-list on the LB is not an authentication boundary, ADR 0012). | Route allow-list. | Store injected and signed by the storefront proxy. |
| Vendure Shop API (`/shop-api`) | **Not exposed.** `InternalOnlyGuard` rejects it without a valid internal HMAC on every host; the storefront does not use it (ADR 0006). The COD payment method's eligibility checker accepts only orders created by our intake service, so no GraphQL path can place an order around quote, spam and rate limits. | — | — |
| Embedded apps (P9.S8b "launch with id-token") | Short-lived (5 min) signed JWT (EdDSA) with `businessId`, `storeId`, `userId`, `appId`, audience = app; JWKS at `api.ourdomain/.well-known/jwks.json`. Apps call the public API with their own installation key. | Installation scopes ∩ the launching user's permissions. | One installation per business. |

**Rate limits** (Redis token buckets, plus Cloudflare at the edge):
- Login, reset and OTP: per IP + per account (10/min, lockout with backoff).
- Admin API: per business, 20 rps sustained, burst 100.
- Public API: per key, 10 rps default, plan-dependent.
- Storefront intake: per (store, device) first, a high per (store, IP) limit (Algerian mobile CGNAT shares IPs), plus a global per-store cap; exceeding any of them holds the order for review, never a 429.
- MCP: dynamic client registration rate-limited per IP and garbage-collected after 30 days unused; per-grant tool-call rate limit.
- Sign-up and trial: Turnstile on sign-up; AI credits and WhatsApp sending unlocked only after email verification (abuse of free credits).
- Details in system-design §4 and §7.

**Cookies and headers**: the dashboard is same-origin with the Admin API (no CORS). `apiOptions.cors` is restricted to `app.ourdomain`. `trustProxy` is set for Cloudflare/LB [VN §1]. HSTS, CSP (nonce-based on storefront; pixels allow-listed), `X-Frame-Options` except the builder preview (frame-ancestors `app.ourdomain`).

## Consequences

### Positive
- Reuses Vendure auth, roles and sessions. Revocation is a session delete.
- Every machine credential is scoped to one business, can be revoked, and is stored hashed.

### Negative
- A custom 2FA strategy and an OAuth server for MCP are ours to build (P10.S2, P9.S8b).

### Risks
- **Bearer tokens in browser storage are exposed to XSS.** Mitigation: strict CSP on the dashboard, no third-party scripts in the dashboard, short-lived sessions for staff.
